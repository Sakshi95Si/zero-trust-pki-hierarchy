# Certificate Templates and Enrollment Methods

In the earlier modules we built the CA hierarchy. This module is about how that hierarchy is actually used: what a certificate will contain, who is allowed to get one, and how the request reaches the CA. In an Enterprise CA environment, both questions are answered by certificate templates and enrollment methods.

The module is split into these topics:

- **Certificate Templates Terminology** - what a template is, its settings, versions and default templates
- **Certificate Enrollment** - the different ways a user, computer or device can request a certificate
- **Certificate Enrollment Strategy** - how to choose methods and design templates for a real environment
- **Module Review**

---

## Certificate Templates Terminology

### What is a certificate template?

A certificate template is an Active Directory object that defines the policy an Enterprise CA applies whenever it issues a certificate. Think of it as a blueprint: it describes what the certificate will look like and who may request it. The template does not issue anything by itself. The CA reads the template, checks the request and the requester against it, and then issues a certificate that follows it.

Key points:

- Templates are stored in Active Directory (in the Configuration partition, under Public Key Services), so all Enterprise CAs in the forest can see them.
- Only an Enterprise CA can issue certificates from templates. A Standalone CA does not use them.
- A template must be published on a CA before that CA will issue from it. The same template can be published on several CAs.
- Each template has a display name, a template name (no spaces, used internally and in command line tools) and a unique object identifier (OID).

### What a template controls

| Setting | What it decides |
|---|---|
| Purpose | User, computer, web server, code signing, smart card logon and so on |
| Validity and renewal period | How long the certificate lives, and how early it can be renewed |
| Subject name | Whether the name is built from Active Directory or supplied in the request |
| Cryptography | Key algorithm, minimum key size, hash and key storage provider |
| Key usage and EKU | What the certificate may be used for |
| Private key options | Whether the key can be exported, archived or must be protected |
| Issuance requirements | Whether manager approval or extra signatures are needed |
| Security (permissions) | Who can read, enroll, autoenroll or manage the template |

### Template versions (schema versions)

Templates come in different schema versions, and the version decides which features are available.

| Version | Introduced with | Main features |
|---|---|---|
| Version 1 | Windows 2000 | Basic, built-in templates. Only the permissions can be changed. No autoenrollment. They cannot be deleted. |
| Version 2 | Windows Server 2003 | Customisable settings, autoenrollment, key archival, superseding templates. |
| Version 3 | Windows Server 2008 | Adds Cryptography Next Generation (CNG) and Suite B algorithms such as ECC and SHA-2 options. |
| Version 4 | Windows Server 2012 | Adds support for key storage providers on more settings, renewal with the same key, and key attestation. Needs a Windows Server 2012 or later CA and Windows 8 or later clients. |

In the console you do not choose the version directly. It is set by the **Compatibility** tab, where you pick the minimum CA version and the minimum certificate recipient (client) version. The higher you set them, the newer the schema and the more options you get, but the fewer older systems can use the template.

> **Best practice:** never edit the built-in version 1 templates. Duplicate the closest template (this creates a version 2 or higher copy) and change the copy.

### Template tabs and important settings

When you open a template's properties, the tabs you will use most are:

- **Compatibility** - minimum CA and recipient versions, as described above.
- **General** - template display name and name, validity period, renewal period, and the option *Publish certificate in Active Directory*.
- **Request Handling** - purpose of the certificate (signature, encryption, or both), *Allow private key to be exported*, renewal with the same key, and prompting the user.
- **Cryptography** - provider category (legacy CSP or Key Storage Provider), algorithm, minimum key size and request hash.
- **Key Attestation** - proves the key is held in a TPM (version 4 templates).
- **Subject Name** - choose *Supply in the request* or *Build from this Active Directory information* (for example common name, DNS name, UPN, email).
- **Server** - options such as not storing the certificate in the CA database, and the security extension used for strong certificate mapping.
- **Issuance Requirements** - CA certificate manager approval and the number of authorised signatures (used with enrollment agents).
- **Superseded Templates** - lists older templates that this one replaces, so autoenrollment can move clients from the old to the new.
- **Extensions** - application policies (Extended Key Usage), key usage, issuance policies and basic constraints.
- **Security** - permissions for each user or group.

### Template permissions

| Permission | Meaning |
|---|---|
| Read | The requester can see that the template exists. Required for enrollment. |
| Enroll | The requester can request a certificate from this template. |
| Autoenroll | The requester can receive the certificate automatically through autoenrollment (this also needs Read and Enroll). |
| Write | Can change the template. Should be limited to PKI administrators. |
| Full Control | Can change everything, including permissions. Limit as much as possible. |

The requester also needs **Enroll permission on the CA itself** (in the CA's Security tab). By default, Authenticated Users have this. Both the template and the CA must allow it.

### Subject name and SAN

- **Build from Active Directory information** - the CA takes the name from the requester's Active Directory object. This is the safe choice for domain users and computers because the requester cannot choose a name they do not own.
- **Supply in the request** - the requester states the name. This is needed for web servers and non-domain devices, but it is a security risk for any template that allows authentication, because someone could request a certificate for another person's name. Combine it with manager approval or tight permissions.
- **Subject Alternative Name (SAN)** - extra names in the certificate, such as DNS names for a web server or the UPN for a user. Modern clients rely on the SAN more than the common name.

### Application policies (EKU) and key usage

The Extended Key Usage list decides what the certificate may be used for. Common values are:

- **Server Authentication** - TLS on a server
- **Client Authentication** - proves a user or device to a server (802.1X, VPN, mutual TLS)
- **Smart Card Logon** - sign in with a smart card
- **Secure Email** - S/MIME signing and encryption
- **Code Signing** - signing software or scripts
- **Encrypting File System** - EFS
- **Document Signing** - signing documents

Key usage is a separate setting, for example Digital Signature or Key Encipherment. A well-designed template includes only what the use case needs.

### Default templates

AD CS ships with many default templates. Some of the common ones are:

| Template | Typical use |
|---|---|
| User | User authentication, EFS and email |
| Computer | Computer authentication for domain computers |
| Web Server | TLS certificate for a web server |
| Domain Controller / Domain Controller Authentication / Kerberos Authentication | Certificates for domain controllers (LDAPS, smart card logon) |
| Subordinate Certification Authority | Issuing certificates to a subordinate CA |
| Code Signing | Signing code |
| Enrollment Agent / Enrollment Agent (Computer) | Requesting certificates on behalf of others |
| OCSP Response Signing | Signing certificate for an Online Responder |
| CEP Encryption / Exchange Enrollment Agent (Offline request) | Support for SCEP/NDES and offline requests |

Most environments issue only a few of these, and create duplicates for their own needs. Unused templates should be removed from the CA.

### Publishing a template

Creating a template and making it available are two different steps:

1. **Certificate Templates console (`certtmpl.msc`)** - create, duplicate and edit templates in Active Directory.
2. **Certification Authority console (`certsrv.msc`)** - right-click *Certificate Templates*, choose *New > Certificate Template to Issue*, and select it. This publishes it on that CA.

After publishing, allow time for Active Directory replication before clients can see it.

## Certificate Enrollment

### What is enrollment?

Enrollment is the process of a requester obtaining a certificate. The basic flow is always the same:

1. The client generates a key pair (the private key stays with the client).
2. The client creates a certificate request with the public key and sends it to the CA.
3. The CA authenticates the requester, checks the template and permissions, and issues or denies the request.
4. The client receives and installs the certificate.

The differences between the methods below are about how the request is made and how the client authenticates.

### Requirements for any enrollment to work

- The client trusts the CA (the root and the intermediate are in the right stores).
- The template is published on the CA, and the requester has Read and Enroll on the template and Enroll on the CA.
- The client can reach the CA (RPC/DCOM for traditional enrollment, or HTTPS for web-based methods).
- The CA can check revocation and the CRL and AIA locations are reachable (Module 02).

### 1. Autoenrollment

Autoenrollment lets domain-joined users and computers get and renew certificates automatically, with no user action.

- Configured by Group Policy: *Public Key Policies > Certificate Services Client - Auto-Enrollment*, set to Enabled, with options to renew expired certificates and update certificates that use templates. There are separate settings for computer and user configuration.
- The template must be version 2 or higher, and the group needs Read, Enroll and Autoenroll permissions.
- The client reads the published templates from Active Directory, checks that it is allowed to use them, and requests a certificate. When the certificate nears the renewal period, it renews automatically.
- Autoenrollment runs during Group Policy refresh and logon. To trigger it manually, use `gpupdate /force` or `certutil -pulse`.

**Best for:** domain-joined users and computers, such as computer certificates for 802.1X or user certificates for email.

### 2. Manual enrollment

The user or administrator starts the request.

- **Certificates console (MMC).** Open `certmgr.msc` (user) or `certlm.msc` (computer), then *All Tasks > Request New Certificate*. The wizard shows the templates the requester is allowed to use. Some templates ask for details such as the name.
- **Command line (certreq).** Create a request file, submit it to the CA and install the response. This is the method used for web servers and for devices that cannot use the wizard.

An example request file (`request.inf`) for a web server:

```ini
[Version]
Signature="$Windows NT$"

[NewRequest]
Subject = "CN=app01.contoso.com"
KeyLength = 2048
Exportable = FALSE
MachineKeySet = TRUE
HashAlgorithm = SHA256

[RequestAttributes]
CertificateTemplate = ContosoWebServer

[Extensions]
2.5.29.17 = "{text}"
_continue_ = "dns=app01.contoso.com&"
_continue_ = "dns=app01&"
```

The commands are:

```
certreq -new request.inf request.req
certreq -submit -config "CAServer\Contoso Issuing CA 01" request.req cert.cer
certreq -accept cert.cer
```

The private key stays on the machine that ran `certreq -new`, so `-accept` must be run on the same machine.

**Best for:** servers and applications, one-off requests, and templates with *Supply in the request*.

### 3. CA Web Enrollment

This is a web site (`/certsrv`) installed with the Certification Authority Web Enrollment role service. Users browse to it, authenticate and submit a request.

- It is simple, but it is an old interface with limited options.
- It must be protected. Use HTTPS, and disable NTLM or enable Extended Protection for Authentication, because HTTP-based enrollment endpoints are open to NTLM relay attacks (known as ESC8).
- Many organisations do not install it at all.

**Best for:** occasional requests where the wizard or certreq is not convenient.

### 4. Enrollment on behalf of another (Enrollment Agent)

An enrollment agent is a trusted person who requests certificates for other users. The agent holds an Enrollment Agent certificate and signs the request for the subject. The template requires the signature through Issuance Requirements.

- Typical use: a help desk or security officer loading smart cards for users.
- It is powerful, so permissions must be restricted to a very small group, and the CA can be configured to limit which templates and subjects each agent can enroll.

### 5. Certificate Enrollment Web Services (CEP and CES)

These two web services let clients enroll over HTTPS without direct RPC/DCOM access to the CA.

- **Certificate Enrollment Policy Web Service (CEP)** - tells the client which templates and CAs are available.
- **Certificate Enrollment Web Service (CES)** - receives the requests and passes them to the CA.

They support several authentication methods (Kerberos, username and password, or a client certificate). They are used for computers that are in another forest, are not domain-joined, or are outside the corporate network (for example, over the internet), and they also support autoenrollment for those clients. HTTPS is required.

### 6. Network Device Enrollment Service (NDES) and SCEP

NDES implements the Simple Certificate Enrollment Protocol (SCEP) for devices that cannot use Active Directory or RPC, such as routers, switches, firewalls and mobile devices.

- The device asks NDES for a certificate over HTTP/HTTPS, usually with a one-time challenge password.
- NDES acts as a registration authority and requests the certificate from the CA on the device's behalf.
- NDES uses its own enrollment agent certificates and special templates, and the NDES service account needs the correct permissions.
- It is also the common path for mobile device management. With Microsoft Intune, a SCEP certificate profile sends the device to an NDES server (through the Intune Certificate Connector) to obtain a certificate. Intune can also use a PKCS profile, where the connector requests the certificate from the CA directly and delivers it to the device.

**Best for:** network devices, non-domain devices and MDM-managed devices.

### Comparison of methods

| Method | Domain joined? | User action | Typical use |
|---|---|---|---|
| Autoenrollment | Yes | None | Domain users and computers |
| Manual (MMC) | Yes | Yes | One-off requests for users or computers |
| Manual (certreq) | Not required | Yes (administrator) | Web servers, applications, custom requests |
| CA Web Enrollment | Not required | Yes | Occasional requests through a browser |
| Enrollment agent | Yes | Agent acts for the user | Smart card provisioning |
| CEP and CES | Not required | None or minimal | Non-domain, other forest or internet clients |
| NDES and SCEP | No | None or challenge password | Network devices and MDM devices |

## Certificate Enrollment Strategy

A strategy is a plan that decides which templates exist, who gets which certificates, and how they are requested, renewed and retired. Without one, a PKI quickly fills up with unused templates, over-permissioned groups and certificates that nobody knows how to renew.

### Step 1: Start from the use cases

List what the organisation needs certificates for, and for each one record who or what needs it and how many there will be.

- Computer authentication (802.1X Wi-Fi, VPN, DirectAccess)
- User authentication and smart cards
- Web servers and internal applications (TLS)
- Domain controller certificates (LDAPS, Kerberos)
- Email signing and encryption
- Code and script signing
- Network devices and MDM devices
- Online Responder (OCSP) signing

Each distinct use case usually becomes one template. Avoid one template for everything.

### Step 2: Choose the enrollment method for each

| Use case | Suggested method |
|---|---|
| Domain computers and users | Autoenrollment through Group Policy |
| Domain controllers | Autoenrollment with a Domain Controller template |
| Internal web servers and applications | certreq or the MMC with an approved Supply-in-request template, or a CLM tool |
| Non-domain and other-forest computers | CEP and CES |
| Network devices | NDES and SCEP |
| Intune-managed devices | SCEP through NDES, or PKCS through the Certificate Connector |
| Smart cards | Enrollment agent |
| Code signing | Manual with restricted permissions and, preferably, an HSM or approval |

### Step 3: Design each template carefully

- Duplicate a default template, never edit version 1 templates.
- Use a clear naming convention, for example `Contoso-Computer-Auth-v2`, and keep a record of every template, its purpose, owner and permissions.
- Set the compatibility to the lowest versions you can accept, and no lower than needed for CNG and modern algorithms.
- Use a modern algorithm and key size: RSA 2048 or higher (or ECC where supported) with SHA-256 or better, and a Key Storage Provider.
- Set the validity by risk. Short validity for high-risk or high-volume uses, and enough renewal time (for example a 1-year certificate with a renewal period of 6 weeks) so a failed renewal is noticed before expiry. Remember that a certificate cannot outlive the CA that issued it.
- Do not allow private key export unless there is a documented reason.
- Use *Build from Active Directory information* wherever possible. Use *Supply in the request* only where needed and protect it with approval or tight permissions.
- Include only the EKUs and key usages that the use case needs.
- Use Superseded Templates when migrating, so autoenrollment replaces old certificates (for example when moving from SHA-1 or small keys to a stronger template).

### Step 4: Control who can enroll

- Give permissions to security groups, never to individuals or to broad groups like Authenticated Users, unless the template is truly meant for everyone.
- Use separate groups per template, for example a computer group for the Wi-Fi certificate, so you can control rollout by adding members.
- Remove Write and Full Control from everyone except PKI administrators.
- Require CA manager approval for sensitive templates.
- Scope autoenrollment Group Policy to the correct OUs or to security-filtered groups, so only the intended devices apply it.

### Step 5: Plan where templates are published

- Publish a template only on the issuing CAs that need it. This limits exposure and spreads the workload.
- In larger environments, consider separate issuing CAs for different purposes, such as one for domain computers and users, one for network and mobile devices, and one for high-assurance uses like code signing.
- Remove default templates that are not in use from every CA.

### Step 6: Prepare for scale and lifecycle

- **CA database growth.** Many certificates with a short validity make the database grow quickly. Plan storage, backup and maintenance.
- **Renewal.** Autoenrollment handles renewal for domain clients. For servers and devices with manual or SCEP enrollment, track expiry dates and automate renewal where possible, with a certificate lifecycle management (CLM) tool or monitoring.
- **Revocation.** Decide how certificates are revoked when a device is lost or a user leaves, and how long CRLs and OCSP take to reflect it (Module 02).
- **Monitoring.** Watch the CA for issuance failures and denied requests, and the client Application log for autoenrollment errors from the `Microsoft-Windows-CertificateServicesClient-AutoEnrollment` source.

### Step 7: Secure the templates and enrollment paths

Most real attacks on AD CS use template misconfiguration, not cryptographic weaknesses. The well-known ones are numbered ESC1 to ESC8 in published research. The main lessons for your strategy are:

- Do not allow *Supply in the request* together with an authentication EKU and broad Enroll permissions. This lets a low-privileged user request a certificate as an administrator.
- Restrict the Certificate Request Agent (enrollment agent) templates and permissions.
- Do not grant low-privileged users Write, Full Control or ownership on templates or the CA.
- Make sure the CA flag that allows a requester-specified SAN (`EDITF_ATTRIBUTESUBJECTALTNAME2`) is turned off.
- Use HTTPS and protections against NTLM relay on any web enrollment, CEP, CES or NDES endpoints.
- Keep the strong certificate mapping protections in place on templates and domain controllers, so a certificate can be tied securely to an Active Directory account.
- Audit your templates regularly with a tool or script, and keep a change process for any new or modified template.

### Troubleshooting enrollment

- **Template not visible to the client.** It is not published on the CA, Active Directory has not replicated, the requester lacks Read or Enroll, or the template version is too new for the client.
- **Request denied.** The requester lacks Enroll permission on the CA or template, or the subject information is missing.
- **Request pending.** The template or CA requires manager approval.
- **Autoenrollment does nothing.** The GPO is not applied, the template has no Autoenroll permission, it is a version 1 template, or the client does not trust the CA.
- **Certificate cannot be used.** The EKU is wrong for the application, the SAN is missing or the revocation check fails.
- **Useful tools:** `certutil -template` (lists templates), `certutil -CATemplates` (templates on a CA), `certutil -pulse`, the CA's Failed Requests and Pending Requests nodes, and the client's Application and CAPI2 logs.

## Module Review

- A certificate template is an Active Directory object that defines the policy for issued certificates. It works only with an Enterprise CA and must be published on the CA to be used.
- There are four schema versions. Version 1 is fixed and has no autoenrollment. Version 2 and above can be customised and autoenrolled. Version 3 adds CNG. Version 4 adds more modern options and key attestation. The Compatibility tab decides which version is created.
- Duplicate templates instead of editing the defaults.
- Template security uses Read, Enroll, Autoenroll, Write and Full Control. The requester also needs Enroll on the CA.
- Build from Active Directory is safe. Supply in the request is risky and needs controls.
- Enrollment methods are: autoenrollment, manual (MMC and certreq), CA Web Enrollment, enrollment agent, CEP and CES, and NDES/SCEP (including Intune).
- A good strategy starts from use cases, chooses the right method for each, creates one tightly scoped template per use, controls permissions with groups, and plans for renewal, scale and monitoring.
- Secure templates and enrollment endpoints against misconfiguration attacks (ESC1 to ESC8), including restricted enrollment agents, HTTPS, and no requester-supplied SANs on authentication templates.

## Common Interview Questions

**What is a certificate template and where is it stored?**
It is an Active Directory object that defines issuance policy for an Enterprise CA. It is stored in the Configuration partition of the forest.

**Why should you duplicate a default template instead of editing it?**
Version 1 templates cannot be changed, and duplicating gives a new, customisable template while leaving the default untouched.

**What permissions are needed for autoenrollment?**
Read, Enroll and Autoenroll on the template, a version 2 or higher template, the autoenrollment Group Policy enabled, and Enroll on the CA.

**What is the difference between Build from Active Directory information and Supply in the request?**
The first takes the name from the requester's AD object. The second lets the requester choose the name, which is needed for web servers but risky for authentication templates.

**How do you issue certificates to computers that are not in the domain?**
Use CEP and CES over HTTPS, NDES with SCEP, an Intune SCEP or PKCS profile, or manual requests with certreq.

**What is NDES used for?**
It implements SCEP so network devices and MDM-managed devices can obtain certificates without Active Directory.

**What is an enrollment agent?**
A trusted account that requests certificates on behalf of other users, for example to provision smart cards. It must be tightly controlled.

**How would you replace an old template with a new one?**
Create the new template, list the old one under Superseded Templates, publish the new one and let autoenrollment replace the certificates, then unpublish the old template.

**A template does not appear for a user. What do you check?**
Whether it is published on the CA, whether AD replication is complete, the user's Read and Enroll permissions on the template and the CA, and the template's compatibility version.

**What is ESC1?**
A misconfiguration where a template allows the requester to supply the subject (SAN), has an authentication EKU and allows low-privileged enrollment, so an attacker can obtain a certificate as another user.
