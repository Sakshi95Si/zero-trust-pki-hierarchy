# Cloud PKI Hierarchy

Until now the modules have focused on an on-premises Microsoft PKI. Many organizations are now moving workloads, devices and identity to the cloud, and the PKI has to follow. This module explains the options for running or extending a PKI in the cloud, with a closer look at Microsoft Cloud PKI (part of Intune), cloud-based HSMs for protecting CA keys, and how to design CDP and AIA locations so cloud and remote clients can always validate certificates.

The module is split into these topics:

- **Integration of PKI With Cloud Providers** - the main design models and what to think about
- **Microsoft Cloud PKI** - the managed PKI service in Microsoft Intune
- **Cloud-based HSMs** - protecting CA private keys with cloud hardware security modules
- **CDP AIA Extensions in Cloud and Module** - hosting revocation and CA certificate data in the cloud
- **Module Review**

---

## Integration of PKI With Cloud Providers

### Why PKI is moving to the cloud

- **Devices are no longer only on the corporate network.** Laptops and phones are Entra joined or managed by Intune and often never touch the domain controllers or the LAN.
- **Workloads run in the cloud.** Virtual machines, containers and services in Azure, AWS or Google Cloud need certificates for TLS, mutual TLS and signing.
- **Less infrastructure to run.** Servers for NDES, web servers for CRLs and HSMs all have an operating and patching cost.
- **Higher availability and reach.** Cloud storage and CDNs make CRLs and CA certificates available from anywhere.

The PKI concepts do not change. A hierarchy, key protection, revocation data and enrollment methods are still needed. What changes is where each component runs and who operates it.

### Main design models

| Model | What it means | Typical fit |
|---|---|---|
| 1. Keep AD CS on-premises, extend to the cloud | The CA stays on-premises. Cloud workloads and remote devices reach it over VPN/ExpressRoute, or through CEP/CES, NDES or the Intune connector. CRLs are published to a cloud location. | Existing PKI with many on-premises dependencies |
| 2. AD CS on cloud virtual machines (IaaS) | The same AD CS roles run on VMs in Azure (or another cloud). You still manage the servers, patching, backup and keys. | Lift and shift, or a hybrid datacentre exit |
| 3. Hybrid hierarchy | An offline root stays on-premises (or is held securely), and one or more issuing CAs run in the cloud, signed by that root. | Large environments needing cloud scale, with existing trust kept |
| 4. Cloud-managed (PKI as a service) | The provider runs the CA. Examples are Microsoft Cloud PKI for Intune devices, AWS Private CA, and Google Certificate Authority Service. | Cloud-native workloads and device certificates with minimal operations |

These models can coexist. For example, many organisations keep AD CS for domain computers and servers, and add Microsoft Cloud PKI for Intune-managed devices.

### Managed CA services at a glance

| Service | Notes |
|---|---|
| Microsoft Cloud PKI (Intune) | Managed root and issuing CAs for Intune devices, SCEP-based issuing, hosted CDP and AIA. Covered in the next section. |
| AWS Private CA | Managed private CA with an API, with CRLs published to an S3 bucket and OCSP available. Protected by AWS-managed HSMs. |
| Google Certificate Authority Service | Managed private CA with a tiered hierarchy and certificate templates, with CRL and OCSP support. |

There is no general-purpose, Windows-template-style CA offered by Azure itself outside Intune Cloud PKI. For general Azure workloads, organisations either run AD CS on Azure VMs or use a third-party or cloud-native CA.

### Design questions to answer first

- **Who needs certificates, and where are they?** Domain-joined servers, Entra-joined or Intune-managed devices, containers, network gear, or external partners?
- **Which enrollment protocol is available?** Domain-joined clients can autoenroll. Cloud-only devices need SCEP or PKCS (Intune), CEP/CES, or ACME-style automation from a supported CA. (Module 04 and Module 05)
- **Where is the trust anchor?** Keep one trusted root across on-premises and cloud if possible, so devices do not need extra trusted roots.
- **Where do the private keys live?** Software on a VM, or an HSM? (See the HSM section.)
- **How will clients reach CDP and AIA?** Cloud-only clients usually cannot use LDAP, so an internet-reachable HTTP location is needed. (See the CDP and AIA section.)
- **Who owns and operates it?** Define roles and administration in the cloud, using Azure RBAC and Privileged Identity Management where appropriate.
- **Availability and recovery.** Use availability zones or regions, and keep backups, and a tested recovery plan (Module 06).
- **Logging and monitoring.** Send CA and key vault logs to your SIEM, such as Microsoft Sentinel or Splunk.
- **Compliance and data location.** Check where keys and logs are held and which standards you must meet.

### Running AD CS on Azure VMs: practical points

- An Enterprise CA must be able to reach Active Directory domain controllers. Plan connectivity, DNS and sites (and consider domain controllers in Azure).
- Treat the VM as Tier 0, with restricted network security groups, no public IP and privileged access only.
- Keep the offline root truly offline. A common design keeps the root as a powered-off VM or a machine stored securely outside the cloud, and the issuing CA online in Azure.
- Use managed disks, backups and zone redundancy for the issuing CA, and keep CA backups in a protected location (Module 06).
- Do not rely on Azure's VM backup alone. Take proper CA backups including the key.
- Use HTTP CDP/AIA hosted in cloud storage or on web VMs, with the DNS alias design from Module 02.
- Monitor with Azure Monitor and Sentinel, forwarding the CA Security log.

### Using certificates from the cloud

- **Microsoft Entra certificate-based authentication (CBA)** lets users sign in with a certificate. Entra must be able to check revocation, which means it needs an internet-reachable CRL (an HTTP CDP). A CDP that exists only as LDAP or on a private network will not work.
- **Intune-managed devices** can receive certificates for Wi-Fi (802.1X), VPN and email through SCEP or PKCS profiles.
- **Cloud services and containers** may use short-lived certificates from a cloud CA or a secrets tool, issued through APIs rather than templates.

## Microsoft Cloud PKI

### What it is

Microsoft Cloud PKI is a cloud-hosted certification authority service built into Microsoft Intune. You create the CAs in the Intune admin center, and Microsoft hosts and runs the CA infrastructure, the registration authority and the revocation and AIA endpoints. It removes the need for on-premises servers such as an issuing CA, NDES and a web server for CRLs, for the purpose of issuing certificates to Intune-managed devices.

It is licensed as part of the Intune Suite or as an add-on, so check the current licensing before planning a rollout.

### What it provides

| Feature | Overview |
|---|---|
| Two-tier hierarchy in the cloud | Create a root CA and one or more issuing CAs from the Intune admin center. Several CAs can exist in the same tenant, and limits apply, so check Microsoft's current documentation. |
| Hosted CDP | Intune hosts the CRL distribution point for each CA. |
| Hosted AIA | Intune hosts the Authority Information Access endpoint for each issuing CA, so relying parties can fetch the parent certificates. |
| Built-in SCEP registration authority | Each issuing CA has a cloud SCEP service. It validates the request against the SCEP challenge from an enrolled device and then asks the issuing CA to sign it. |
| Bring your own CA (BYOCA) | An Intune issuing CA can be anchored to your own private root CA, such as AD CS or a non-Microsoft PKI, instead of a Cloud PKI root. |

### Deployment models

**Option 1: Cloud root CA (full cloud PKI).** A new root CA and issuing CA(s) are created in the cloud. This is the simplest option and suits a new, cloud-focused device PKI. You must deploy the new root and issuing CA certificates to devices as trusted certificates.

**Option 2: Bring your own CA (BYOCA).** You create a Cloud PKI issuing CA that chains to your existing private root. Intune generates a certificate signing request (CSR). You sign it with your existing CA (for example your AD CS root or issuing CA) and upload the signed certificate back. Devices that already trust your root automatically trust the certificates from the cloud issuing CA, so there is no new root to distribute.

Both models can exist in the same tenant.

### Important points about BYOCA and AIA

When you use BYOCA, the AIA extension in the issued certificates reflects what your existing parent CA is configured with. AD CS publishes an LDAP AIA location by default. Entra-joined Windows devices and non-Windows platforms cannot follow an LDAP AIA, so they will not be able to fetch the issuing CA certificate to build the chain. Make sure your on-premises CA has an HTTP AIA and CDP that is reachable from the internet before you go down the BYOCA path, or deploy the full chain (root and issuing certificates) to devices as trusted certificates.

### How enrollment works

1. In Intune, create the trusted certificate profiles (root, and preferably issuing CA) and assign them to devices.
2. Create a SCEP certificate profile that points to the Cloud PKI issuing CA. The SCEP URL is filled in for you.
3. The device is told by Intune to request a certificate and sends a CSR with a SCEP challenge to the cloud SCEP service.
4. The validation service checks that the challenge came from an enrolled device and has not been tampered with.
5. The validated request goes to the issuing CA, which signs and returns the certificate.
6. The device installs the certificate and renews it automatically before it expires.

Deploy the trusted certificate profile **before** the SCEP profile, so the device trusts the chain when it receives its certificate.

### Limits and things to know

- Certificates are issued to Intune-managed devices through SCEP. It does not offer other protocols or general enrollment for servers and applications, so it does not replace AD CS for all uses.
- Reported limitations include no OCSP service. Revocation is through the Intune-hosted CRL.
- You do not get the level of control that you have with AD CS (custom templates, exit modules, your own HSM). The CA keys are managed by Microsoft.
- CA lifecycle still matters. Cloud PKI supports staged CA renewal: start planning at the CA's half-life, validate the new CA through its temporary SCEP URL, and activate it only after trust distribution and relying-party tests succeed.
- Network devices, RADIUS servers and other relying parties must trust the Cloud PKI root and issuing CA certificates. Plan how they obtain them.
- Permissions are controlled through Intune roles (for example, a specific permission to create CAs), and it is good practice to use a custom role together with Privileged Identity Management.

### When to choose Cloud PKI or AD CS

| Situation | Suggestion |
|---|---|
| Cloud-only or Intune-managed devices needing Wi-Fi, VPN or email certificates, with a desire for minimal infrastructure | Cloud PKI |
| Need to keep the existing root and trust chain but move device issuing to the cloud | Cloud PKI with BYOCA |
| Domain computers, domain controllers, servers, custom templates, exit modules, or your own HSM | AD CS (on-premises or on IaaS) |
| Many protocols, ACME, or non-Intune devices | AD CS with NDES/CEP/CES, or another CA product |

Many organisations run both: AD CS for the domain and Cloud PKI for devices.

## Cloud-based HSMs

### Why use an HSM in the cloud

As covered in Module 03, the CA private key is the most valuable asset in a PKI. A hardware security module (HSM) protects it so that it cannot be copied out of the device. A cloud HSM gives that protection without owning and housing physical appliances, and with cloud availability and scaling. The CA signs by sending data to the HSM, and the key never leaves it.

### Common options

| Provider | Services | Notes |
|---|---|---|
| Microsoft Azure | Azure Key Vault (Standard uses software keys, Premium uses HSM-backed keys), Azure Key Vault Managed HSM, Azure Cloud HSM | Managed HSM is a single-tenant, FIPS 140-3 Level 3 validated service with full customer control. Azure Cloud HSM is a single-tenant cluster suited to PKCS#11 and lift and shift from on-premises HSMs, and it is the successor to Azure Dedicated HSM, which is being retired. |
| AWS | AWS KMS, AWS CloudHSM | KMS is a managed key service backed by HSMs. CloudHSM gives single-tenant HSM clusters with PKCS#11 and Windows key storage provider interfaces. AWS Private CA can use HSM-resident keys. |
| Google Cloud | Cloud KMS, Cloud HSM | Per-key choice of software or HSM protection, with a single-tenant option available. |

Validation levels change over time. Azure Key Vault Premium and Managed HSM, AWS KMS and CloudHSM use FIPS 140-3 Level 3 validated hardware, while Azure Key Vault Standard uses software protection at a lower level. Google Cloud HSM has been described as validated to FIPS 140-2 Level 3. NIST moved FIPS 140-2 certificates to its Historical list in September 2026, so confirm that your chosen service holds a current FIPS 140-3 certificate if you have a compliance requirement.

### Multi-tenant versus single-tenant

- **Multi-tenant services** (such as Key Vault Premium or KMS) share HSM hardware between customers, with logical isolation. They are simpler and cheaper.
- **Single-tenant services** (such as Managed HSM, Azure Cloud HSM, AWS CloudHSM) give dedicated hardware or partitions, more control over the key hierarchy, and stronger isolation. They cost more and have more operational responsibility.

For a root CA or other very high-value key, a dedicated, single-tenant option is the usual choice. For issuing CAs and workloads, a shared HSM-backed service may be enough, depending on policy.

### Using a cloud HSM with AD CS

AD CS needs a Key Storage Provider (KSP, based on CNG) or a legacy CSP to talk to the key store, so not every cloud key service can be used directly.

- Options that provide a KSP or PKCS#11 interface (such as AWS CloudHSM and Azure Cloud HSM, or third-party HSMs hosted in the cloud) are the typical fit. During CA installation you select the HSM's provider instead of the Microsoft Software Key Storage Provider.
- API-based key vaults (for example Azure Key Vault and Managed HSM) do not present a standard Windows KSP by themselves. Using them as the CA signing key store needs a supported vendor or third-party integration, so verify support before designing around it.
- The provider and key cannot be changed later without a new CA key, so decide before installation (Module 03).
- Plan network access to the HSM (private connectivity), authentication (HSM users and credentials), high availability (more than one HSM or zone) and backup and recovery (such as the HSM's own backup mechanism and key custody).

### Using a cloud HSM with managed CAs

- AWS Private CA and Google CAS protect CA keys in provider-managed HSMs as a built-in feature, so you do not select an HSM yourself, unless a specific option exists for customer-controlled keys.
- Microsoft Cloud PKI keys are managed by Microsoft as part of the service.

### Cloud HSM design checklist

- Does the key need to be exportable or portable? (Often no, by design.)
- Who controls the key and the HSM administrator credentials? Define roles, and consider M-of-N approval for sensitive actions.
- Is single-tenant isolation required by policy?
- Are the latency and cost per signing operation acceptable for your issuance volume?
- Is there a recovery plan if the HSM, region or subscription is lost?
- Are logs of key use sent to your monitoring system?
- Is the service on a current validation list for your compliance needs?

## CDP AIA Extensions in Cloud and Module

Module 02 showed how CDP and AIA extensions work and Module 03 how to configure them for a two-tier CA. In the cloud, the same rules apply, and the question becomes where to host the files so every client can reach them.

### Rules that stay the same

- CDP and AIA are written into certificates at issuance time, so design them before the first certificate is issued.
- Use HTTP and a DNS alias that you control (for example `pki.contoso.com`), never the name of a specific server.
- Include HTTP URLs in both extensions. Cloud-only, Entra-joined and non-Windows clients cannot follow LDAP URLs.
- Keep the CRL and AIA files current after every publication.
- Make sure both CRLs in a two-tier hierarchy (root and issuing) are published and reachable.

### Hosting CDP and AIA in Azure

A common approach is to use Azure Blob Storage:

1. Create a storage account and enable the static website feature (this creates the `$web` container), or use a normal container with public blob access.
2. Allow anonymous read access to the files. They are public by design and signed, so no secrets are exposed.
3. Map a custom domain (the DNS alias) to the storage endpoint, so the URL in the certificates stays the same if the storage changes.
4. The CDP and AIA URLs need plain HTTP. If the storage account requires secure transfer (HTTPS only), HTTP clients will fail. Turn this setting off for the account or the endpoint that serves PKI files, or use a front end that serves HTTP.
5. Optionally, place Azure Front Door or Azure CDN in front for lower latency and caching. Be careful with the caching time (see below), and note that a front end that forces HTTPS redirects will break HTTP-only PKI URLs.
6. Upload the root and issuing CA certificates (AIA) and the CRLs and delta CRLs (CDP) to the container.

**Publishing the files.** The CA writes CRLs to its local `CertEnroll` folder. A script or scheduled task then copies the files to storage after each publication. A typical approach is a small PowerShell script on the CA that runs `certutil -crl` and uploads the files with AzCopy, scheduled more often than the CRL publication interval. The identity used should have only the permission needed to write blobs (for example the Storage Blob Data Contributor role, preferably through a managed identity).

The same idea works in AWS (an S3 bucket behind CloudFront or a website endpoint with Route 53 DNS) and Google Cloud (Cloud Storage behind a load balancer or CDN).

### CA configuration example

The CA publishes locally and includes the cloud HTTP URL in issued certificates. For an issuing CA, the settings look like this:

- **CDP:** local path with flags to publish the CRL and delta CRL, plus `http://pki.contoso.com/pki/%3%8%9.crl` with flags to include it in issued certificates and in the CRL for delta lookup
- **AIA:** local path, plus `http://pki.contoso.com/pki/%1_%3%4.crt` with the flag to include it in issued certificates
- **OCSP URL in AIA**, if an Online Responder is deployed (for example `http://ocsp.contoso.com/ocsp`)

See Module 02 for the flag values.

### Delta CRL names and the plus sign

Delta CRL file names contain a plus sign (the `%9` variable adds it). Some web servers and storage services treat this character in a special way, such as in URL encoding. Always test that the delta CRL URL really downloads from a client, as well as the base CRL.

### Caching, overlap and freshness

CDNs and caches improve speed but can hold old copies of a CRL. If the cache lifetime is longer than the CRL's overlap period, clients may receive an expired CRL even though the new one has been uploaded. To avoid this:

- Set the cache time (TTL) shorter than the CRL overlap and much shorter than the delta CRL period.
- Purge the cache after an urgent CRL publication.
- Include the HTTP location in your monitoring, so a stale file is noticed.

### Availability and resilience

- Use zone-redundant or geo-redundant storage, or multiple regions behind a DNS or CDN failover, for any production PKI.
- Keep the PKI content on a separate storage account from application data, with its own access policies.
- Protect against accidental deletion with soft delete, versioning and resource locks.
- Limit write access to the CA and PKI administrators. Everyone else can only read.
- Keep a copy of the files outside the cloud service, so you can rebuild if the storage is lost.

### Online Responder (OCSP) in the cloud

If you use OCSP, the Online Responder role can run on VMs in the cloud behind a load balancer, reading the CRLs from the HTTP location. Use more than one responder, in different zones, and monitor the signing certificate and CRL retrieval as described in Module 02 and Module 06. Microsoft Cloud PKI does not offer OCSP, so it depends on the hosted CRL.

### Microsoft Cloud PKI and its endpoints

With Microsoft Cloud PKI, Intune hosts the CDP and AIA for you. The endpoints are written into the certificates automatically. You can copy the CDP, AIA and SCEP URIs from the CA properties if you need to allow-list them in firewalls or proxies, or give them to partners. The hosted SCEP endpoint is under a Microsoft namespace that is normally already allowed in enterprise networks. With BYOCA, the parent CA's own CDP and AIA still apply for the upper part of the chain, so those must be reachable too.

### Cloud CDP/AIA troubleshooting

- **Revocation offline errors on cloud or remote devices.** Check that an HTTP CDP exists in the certificates and is reachable from the internet, and that no HTTPS redirect, firewall or storage firewall blocks it.
- **Chain errors on Entra-joined or non-Windows devices.** Check the AIA. An LDAP-only AIA cannot be followed. Deploy the issuing certificate as a trusted certificate, or publish an HTTP AIA.
- **Old CRL being served.** Check the CDN or cache TTL, and compare the file's Next Update with the current time.
- **Delta CRL fails.** Check the plus sign handling and the file name.
- **Custom domain not working.** Check the DNS alias, and that the storage account or front end accepts the host name.
- Use the tools from Module 02, such as `certutil -urlfetch -verify`, from a client in the same network position as the failing device.

## Module Review

- A cloud PKI changes where components run and who operates them, not the PKI fundamentals.
- **Main models:** AD CS stays on-premises and extends to the cloud, AD CS on cloud VMs, a hybrid hierarchy with an offline root and cloud issuing CAs, and managed CA services such as Microsoft Cloud PKI, AWS Private CA and Google CAS.
- **Microsoft Cloud PKI** provides cloud root and issuing CAs for Intune devices, with a hosted CDP and AIA and a built-in SCEP registration authority. It can also work with BYOCA, anchoring an issuing CA to your own root through a CSR.
- **Cloud PKI limits:** SCEP for Intune-managed devices only, no OCSP, less control than AD CS, and CA renewal must be planned (staged renewal). Deploy trusted root and issuing certificates before SCEP profiles.
- With BYOCA, make sure the parent CA publishes an HTTP, internet-reachable AIA and CDP, because LDAP cannot be followed by Entra-joined and non-Windows devices.
- **Cloud HSMs** protect CA keys without owning appliances. Examples: Azure Key Vault Premium, Managed HSM and Azure Cloud HSM, AWS KMS and CloudHSM, and Google Cloud KMS and HSM. Choose single-tenant options for the most sensitive keys, check current FIPS 140-3 validation, and confirm KSP or PKCS#11 support if the HSM must work with AD CS.
- Host CDP and AIA over plain HTTP in cloud storage (for example Azure Blob static website) behind a custom DNS alias, optionally with a CDN. Upload CRLs and CA certificates with a script after each publication.
- Watch for cache lifetimes, HTTPS redirects, the plus sign in delta CRL names, and keep storage redundant, protected and monitored.

## Common Interview Questions

**What are the main ways to run a PKI in the cloud?**
AD CS on-premises extended to the cloud, AD CS on cloud VMs, a hybrid hierarchy with an offline root and cloud issuing CA, or a managed PKI service such as Microsoft Cloud PKI, AWS Private CA or Google CAS.

**What is Microsoft Cloud PKI?**
A cloud-hosted CA service in Intune with root and issuing CAs, a hosted CDP and AIA, and a SCEP registration authority for Intune-managed devices.

**What is BYOCA in Cloud PKI?**
A cloud issuing CA anchored to your own private root. Intune creates a CSR, you sign it with your CA, and upload the certificate.

**What is the main trap with BYOCA and AD CS?**
The default LDAP AIA cannot be followed by Entra-joined and non-Windows devices, so an HTTP AIA and CDP reachable from the internet are needed.

**Does Cloud PKI support OCSP?**
No. It relies on the hosted CRL, and it issues through SCEP to Intune-managed devices.

**Why use an HSM for CA keys, and why in the cloud?**
An HSM stops the key being copied. A cloud HSM removes the cost of owning appliances and adds availability, while still keeping the key inside validated hardware.

**What is the difference between Key Vault, Managed HSM and Cloud HSM in Azure?**
Key Vault is multi-tenant (Premium is HSM-backed), Managed HSM is a single-tenant FIPS 140-3 Level 3 HSM service, and Azure Cloud HSM is a single-tenant cluster for PKCS#11-based lift and shift, replacing Dedicated HSM.

**Can AD CS use Azure Key Vault directly for its CA key?**
Not by itself. AD CS needs a KSP or CSP, so you need an HSM that offers one (for example a cloud HSM with a vendor KSP), or a supported integration.

**How do you host CDP and AIA in Azure?**
In a storage account with the static website feature and anonymous read, a custom domain DNS alias, plain HTTP, and a script that uploads CRLs and certificates after each publication.

**Why must CDN caching be controlled for CRLs?**
A cached CRL can expire while a new one exists, causing revocation errors. The cache time must be shorter than the CRL overlap.

**Why is a HTTP location required for cloud devices?**
LDAP locations work only for domain-joined clients inside the network. Cloud-only and non-Windows clients need a public HTTP URL.
