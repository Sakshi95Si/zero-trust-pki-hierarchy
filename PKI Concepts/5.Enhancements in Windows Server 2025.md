# Enhancements in Windows Server 2025

This module covers the AD CS improvements you can use on a Windows Server 2025 PKI. It has two parts: the enrollment and availability features introduced in Windows Server 2012 and 2012 R2 (site awareness, IDN, lifecycle notifications, key-based renewal), which continue to work on 2025, and the newer 2025-era updates (partitioned CRLs, larger certificate extensions, richer audit events and post-quantum signatures) that bring AD CS up to date for large, security-sensitive environments.

The module is split into these topics:

- **Introduction** - where these enhancements come from and what they give you
- **What's New in AD CS on Windows Server 2025** - partitioned CRLs, larger extensions, audit logging, hardening, post-quantum signatures and upgrade notes
- **ADCS Site Awareness** - sending enrollment requests to a nearby CA
- **IDN and CLM** - Internationalized Domain Names and Certificate Lifecycle Notifications
- **Key Based Renewal** - automatic renewal for computers outside the domain
- **Module Review**

---

## Introduction

### A note on where these features come from

The classic features in this module (site awareness, IDN support, certificate lifecycle notifications and key-based renewal) were introduced in Windows Server 2012 and 2012 R2 and are fully supported on Windows Server 2025. What is new in the 2025 generation is a separate set of updates, covered in the next section. Some of them were delivered as monthly updates that also reached Windows Server 2019 and 2022, while others (such as ML-DSA) are for Windows Server 2025 only. If an interviewer asks, you can say: the 2012-era features are still supported, and the newer CRL partitioning, audit and post-quantum features come from 2025-era updates.

### Why these enhancements matter

| Enhancement | Problem it solves |
|---|---|
| Site awareness | Clients may enroll from a distant CA over a slow WAN link. |
| IDN support | Names with non-English characters could not be used in certificates and CRL/OCSP locations. |
| Certificate lifecycle notifications | Expired certificates cause outages because nobody is told in time. |
| Key-based renewal | Computers outside the domain needed manual renewal. |

### Other improvements available since Windows Server 2012

These are not in the module list, but they come from the same set of enhancements and are worth knowing:

- **All role services on any edition and on Server Core.** All six AD CS role services can be installed on any edition, and on Server Core or Minimal Server Interface. Installation is split into installing the role and then running the configuration wizard or the PowerShell deployment cmdlets (for example `Install-AdcsCertificationAuthority`).
- **Version 4 certificate templates** with the Compatibility tab, which can require renewal with the same key. This keeps a TPM-protected key on the TPM after renewal.
- **TPM key attestation.** The CA can verify that a private key is protected by a hardware TPM before issuing.
- **Encrypted certificate requests by default.** A 2012 or later CA enforces encryption of requests (the RPC packet privacy setting, `IF_ENFORCEENCRYPTICERTREQUEST`), so request details cannot be read on the network. Very old clients such as Windows XP cannot enroll with this setting.
- **Group-protected PFX.** A PFX file can be protected for a user or group instead of a password.
- **CA private key included in System State backup**, plus the PowerShell cmdlets `Backup-CARoleService` and `Restore-CARoleService` for the CA database.

## What's New in AD CS on Windows Server 2025

Windows Server 2025 reached general availability on 1 November 2024, and its AD CS role has gained several important features through updates since then. Some of them also reached Windows Server 2019 and 2022, so check the table before assuming a feature is exclusive to 2025.

### Windows Server 2025 at a glance

| Enhancement | Arrived with | Available on | What it gives you |
|---|---|---|---|
| Partitioned CRLs | October 2025 update (14 October 2025) | Windows Server 2019 (KB5066586), 2022 (KB5066782) and 2025 (KB5066835) | Splits one large CRL into many smaller ones |
| Larger extensions and database limits | Late 2025 updates | Reported for supported CAs after the update | Certificates can carry extensions above 4 KB, which prepares AD CS for bigger post-quantum data |
| Expanded audit events | 2025 updates | Windows Server 2025 and updated earlier versions | New fields in events 4886 to 4889 for investigation and SIEM use |
| ML-DSA post-quantum signatures | May 2026 update (KB5087539) | Windows Server 2025 only (build 26100.32860 or later) | Issue certificates signed with quantum-resistant algorithms |
| Updated hardening guidance | 2025 | All versions | NTLM relay protection, HSM and template controls |
| 32K Active Directory database pages | Windows Server 2025 | Windows Server 2025 forest and domain functional level | Larger directory objects, relevant to the AD that your Enterprise CA publishes into |

Notes on the table:

- The partitioned CRL update numbers come from the author of the Sysadmins LV series on partitioned CRLs. Always confirm the exact KB for your build in the Microsoft Update Catalog.
- The details of the larger extension limit and the audit fields come from a vendor write-up of Microsoft's 2025 changes, so check them against Microsoft's current documentation before relying on them in production.
- Windows Server 2025 follows the fixed lifecycle policy, with mainstream support ending on 13 November 2029 and extended support on 14 November 2034, according to one summary of the release. Check Microsoft's lifecycle page for the final dates.

### Partitioned CRLs

**The problem.** A CRL lists every unexpired revoked certificate that a CA has issued over its lifetime, which can be decades. Large CAs end up with CRLs of tens of megabytes (the author of the Sysadmins LV series reports having seen 50 MB or more). Every client that validates a certificate must download and decode that file, which slows logons, VPNs and load balancers. Delta CRLs (Module 02) help, but a client still has to fetch the big base CRL whenever its cached copy expires.

**The idea.** A partitioned CRL splits one CRL into a set of smaller ones:

1. You choose a number of partitions, for example 10 or 100.
2. When a request arrives, the CA assigns the new certificate to a partition, using random or round-robin allocation.
3. The CDP extension of that certificate points to its own partition's CRL.
4. If the certificate is revoked, it appears only in that partition's CRL.

The client behaviour does not change. It follows the CDP URL in the certificate and downloads a CRL, which happens to be smaller. This means no client update is needed, which is the main reason it is practical. Random assignment also spreads revoked certificates more evenly than the older RFC 5280 method of splitting by revocation reason. With small partitions, some organisations may be able to stop using delta CRLs and simply publish the base partitions more often.

**Enabling it.** The feature is optional and is meant for organisations with a high volume of revocations or very large CRLs. A vendor guide to the 2025 updates describes enabling it from the command line like this, then restarting the CA service:

```
certutil -setreg ca\CRLFlags +0x00400000
certutil -setreg ca\CRLMaxPartitions 10
net stop certsvc && net start certsvc
```

To roll back, remove the flag with `certutil -setreg ca\CRLFlags -0x00400000` and restart the service. Treat these registry names as a starting point and check them against Microsoft's documentation and a lab CA before production, because the feature is new and the details have been updated since it was released.

**Design points**

- **HTTP only.** Partitioned CRLs do not work with LDAP CDP URLs. One published analysis says the CA will fail to start if partitioning is enabled while an LDAP URL is still configured, and the guidance was revised later, so remove LDAP CDP locations before enabling it and check the current guidance.
- The CDP URL must be able to point to the correct partition file for each certificate, so use the variables and file naming in Microsoft's guidance, and publish all partitions to your web servers (Module 02 and Module 07).
- Choose the partition count by the number of revoked certificates you expect, so that each partition stays a manageable size.
- Test with your oldest clients and applications and with monitoring, as with any CDP change. Validation is a client behaviour, so verify with `certutil -urlfetch -verify` on a certificate from each partition.
- Update monitoring so that every partition's CRL is checked for expiry (Module 06).

### Larger certificate extensions and database limits

Older AD CS versions limited a certificate extension to about 4 KB. Updates from late 2025 remove that limit, and one report also describes support for larger database pages, so the CA database and certificates can carry more data. This matters because:

- Complex policy and identity extensions (for example many issuance policies or custom attributes) fit without trimming.
- Post-quantum data is much bigger. ML-DSA public keys and signatures are several kilobytes, compared with a few hundred bytes for RSA (Module 08).
- The CA database needs room for larger rows as certificates grow.

A vendor guide describes enabling the higher extension limit with a registry flag (`certutil -setreg DBFlags +0x1000`, followed by a service restart), with a matching command to revert. As with partitioning, test it on a lab CA first, because older applications and parsers may not handle larger extensions, and take a database backup before the change (Module 06).

### Expanded audit logging

AD CS audit events were extended so security teams can see more about each request. The events are:

| Event | Meaning |
|---|---|
| 4886 | Certificate Services received a certificate request |
| 4887 | A request was approved and a certificate issued |
| 4888 | A request was denied |
| 4889 | A request was set to pending |

New fields reported for these events include:

- **Subject and SAN from the CSR** - what the requester asked for, which can be compared with what was issued.
- **Requested template** - the template named in the request.
- **Client details** such as operating system version, the cryptographic provider and client information. These are provided by the client and are not to be used for security decisions, only for context.
- **Authentication service and level** - whether the requester used NTLM, Kerberos or Schannel, and the RPC authentication level.
- **DCOM or RPC** - the protocol used to reach the CA.
- For issued certificates (4887): the SAN, the template and the serial number.

The `Disposition` value in events 4887 to 4889 shows the outcome of the request, with common values 20 (issued), 30 (failed), 31 (denied), 9 (pending) and 21 (revoked).

**Why this matters:** the new data helps detect misuse of certificate templates, such as a request whose SAN names a privileged account, or requests arriving over NTLM. Update your SIEM parsers and alerts (Splunk, Microsoft Sentinel or similar) to read the new fields, and build a baseline of normal issuance first (Module 06).

### Updated hardening guidance

Certificate Authorities are Tier 0 assets, and Microsoft's 2025 guidance repeats and sharpens the main controls (see also Module 03 and Module 04):

- **Protect the CA key with an HSM**, preferably FIPS 140-3 Level 3. FIPS 140-2 validations moved to NIST's Historical list on 21 September 2026, according to the vendor guide, so check the current status of your HSM.
- **Cut the attack surface.** Remove unused templates, give Enroll and Autoenroll only to specific groups (not Authenticated Users or Domain Users), and avoid Supply in the request unless approval and monitoring are in place.
- **Protect web enrollment against NTLM relay.** Use HTTPS and Extended Protection for Authentication on CA Web Enrollment, CES, CEP and NDES, and apply the mitigations in Microsoft's KB5005413 (the PetitPotam guidance).
- **Audit regularly.** Review ACLs on templates and CA objects, and monitor enrollment using the expanded audit events above.
- **Plan for the end of NTLM.** Check how much NTLM your certificate enrollment still uses and move to Kerberos or certificate-based authentication where you can.

### Post-quantum signatures (ML-DSA)

AD CS on Windows Server 2025 can now issue certificates that use the NIST post-quantum signature algorithm ML-DSA (FIPS 204). This arrived with the May 2026 security update, KB5087539 (build 26100.32860 or later).

| Point | Detail |
|---|---|
| Algorithms | ML-DSA-44, ML-DSA-65 and ML-DSA-87, which appear in the algorithm name list when you configure a CA |
| Supported OS | Windows Server 2025 with the update. Microsoft's overview lists no support for 2019 or 2022, and no backport is expected |
| Not yet in AD CS | ML-KEM and composite (classical plus post-quantum) algorithms are listed as planned for a later phase |
| Platform support | ML-KEM and ML-DSA reached general availability in the Windows cryptography (CNG) APIs on Windows Server 2025 and Windows 11 in late 2025 |
| Key storage | HSM vendors need PQC firmware and a key storage provider. Older HSMs may need replacing |

In practice this means a PQC pilot needs new CAs on Windows Server 2025. Treat it as an evaluation for now: use it in a lab or for non-critical uses such as code signing, watch client and application support, and see Module 08 for the migration plan.

### Active Directory changes in Windows Server 2025

A few Windows Server 2025 changes affect the Active Directory that an Enterprise CA publishes into. They do not change the CA database:

- Optional **32K database page size** for AD DS (the old format used 8K pages). It gives larger objects and many more values in multivalued attributes, such as the `userCertificate` attribute.
- It needs the new domain and forest functional level, every domain controller on Windows Server 2025, and it is not enabled by default and cannot be undone once enabled.
- Because it is a forest-wide, irreversible change, plan it with your Active Directory team and do not link it to a CA upgrade.

### Moving AD CS from Windows Server 2022 to 2025

- Decide between an in-place upgrade and a migration to a new server. A migration is cleaner, but the CA name, CRL and AIA locations must stay the same so that existing certificates keep working. Use the DNS alias for CDP and AIA (Module 02) so URLs do not change.
- Take a full CA backup first, including the key, database and registry configuration, and test a restore (Module 06).
- Install the latest cumulative updates before judging features, because several of the features above arrive through updates and not through the operating system itself.
- Test new features one at a time in a lab CA, in this order: audit logging (low risk), larger extensions, partitioned CRLs, then ML-DSA on a separate test hierarchy.
- Update dependent tools such as monitoring, SIEM parsers, CLM products (Module 08) and HSM drivers.
- Check that the Online Responder, NDES, CEP and CES servers are patched to the same level, and keep the offline root's patching schedule (Module 06).
- Windows Server 2022 remains supported for the existing AD CS features and for partitioned CRLs, but not for ML-DSA.

## ADCS Site Awareness

### The problem

In an organisation with several offices, there may be Enterprise CAs in more than one location. By default, a client does not necessarily choose the closest one, so a user in a branch office could enroll through a CA in a distant data centre across a slow or congested link. If that far CA is down, enrollment can also fail or take much longer.

### What site awareness does

Site awareness lets certificate clients use Active Directory sites to find a CA in their own site, or the nearest one in terms of site link cost. It improves enrollment speed, reduces WAN traffic and spreads the load across CAs.

It is available for Windows 8 and Windows Server 2012 and later (including Windows Server 2022 and 2025). It is not enabled by default on the CA side, because the CAs have to be told which site they belong to.

### How it works

1. When a client enrolls for a template-based certificate, it queries Active Directory for the template and for the Enterprise CA objects.
2. The client finds out its own AD site name.
3. For each CA that has a site name configured, the client works out the site link cost from its own site to the CA's site.
4. The client orders the CAs that allow it to enroll and that publish the template it needs, with the lowest cost first.
5. It tries the cheapest CA first. If that CA does not respond, it moves to the next one.

Important rules:

- CAs with the same cost are ordered randomly, which spreads the load evenly between them.
- A CA with no site name configured gets the highest possible cost, so it is tried last.
- If no CA that allows enrollment and publishes the template responds, the request fails.
- Only Active Directory queries are used to calculate the order. No CA is contacted until the client starts the request.
- The client side is enabled by default on Windows 8 and later, so nothing needs to be configured on those clients. Older clients (Windows Vista and Windows 7) use a different mechanism that needs a registry setting on the client.

### Enabling site awareness on the CA

The CA's site is stored in the `msPKI-Site-Name` attribute of the CA object. The object is in the Enrollment Services container in the Configuration partition of Active Directory (under Public Key Services).

To set it automatically for all Enterprise CAs in the forest, using their current AD site, run:

```
certutil -f -setcasites set
```

To set it for one specific CA:

```
certutil -setcasites -f -config "<CAConfigName>" <SiteName>
```

The CA config name is the server name and CA name, for example `CA1.contoso.com\Contoso Issuing CA 01`. You can see it by running `certutil` with no parameters.

To check the result and the site costs from a client, use:

```
certutil -ping "CA1.contoso.com,CA2.contoso.com"
```

### Design points

- Make sure the AD sites and subnets are defined correctly, and that site link costs reflect the real network. Site awareness is only as good as the AD site configuration.
- Publish the same templates on the CAs in each major site, so clients have a nearby choice.
- If you move a CA to a new site, update its site name with `certutil -setcasites`.
- Site awareness decides which CA a client uses for enrollment. It does not change where CRLs or AIA files are downloaded from, so keep the CDP and AIA design in Module 02 in mind as well.

## IDN and CLM

### Internationalized Domain Names (IDN)

An internationalized domain name contains characters that cannot be written in basic ASCII, such as accented letters, or Chinese, Arabic, Cyrillic or Japanese characters. A DNS name such as a company website in a local script is an IDN.

In certificates and DNS, these names are stored in an ASCII form called **punycode** (for example `xn--...` names). The user sees the readable name, but the encoded form is what is actually stored.

Windows Server 2012 and later, including Windows Server 2022 and 2025, support IDNs in these AD CS scenarios:

- Certificate enrollment for computers that use IDNs
- Creating and submitting a request containing an IDN with the `certreq` command line tool
- Publishing CRLs and OCSP to servers that use IDNs, so CDP, AIA and OCSP URLs can use IDN host names
- The Certificate dialog and the Certificates MMC snap-in can display and accept IDNs in certificate properties

Note that Microsoft describes this as limited support for the scenarios above, so test any IDN design before relying on it, especially with third-party devices and applications.

**Why it matters:** organisations in regions with non-Latin scripts can use their local-language host names in server certificates and in revocation URLs without workarounds.

### CLM: Certificate Lifecycle Notifications

In this module, CLM refers to **certificate lifecycle notifications**, the Windows feature that raises an event when something happens to a certificate. It should not be confused with third-party Certificate Lifecycle Management products, such as discovery and automation platforms, which are a different thing, although the abbreviation is the same. (If your course material means the broader management tools, tell me and I will add a section on them.)

Available on Windows 8 and Windows Server 2012 and later, certificates in the Personal (MY) store can generate notifications for events such as:

- A certificate is new (enrolled)
- A certificate is renewed or replaced
- A certificate is close to expiry, or has expired
- A certificate is deleted, archived or exported

Expiry notification also works for stores other than the Personal store.

### What you can do with them

- **Trigger a script or program when an event happens.** For example, restart a service or update an IIS binding when its certificate is renewed, or send an email when a certificate is close to expiry.
- **Manage certificates remotely with PowerShell:** view, install, copy, request and delete certificates and their private keys on remote computers, which helps with server farms.
- **Let applications reconfigure themselves** automatically when a certificate is renewed or replaced, either by autoenrollment or by an administrator.

### Why it matters

Most certificate outages are caused by a certificate that expired without anybody noticing, or by a renewed certificate that the application never started using. Lifecycle notifications help prevent both. They are a basic, built-in alternative to a full lifecycle management product, and they work well together with autoenrollment.

## Key Based Renewal

### The problem

Autoenrollment handles renewals for domain-joined computers through Active Directory. But computers in workgroups, in an untrusted forest, or in a perimeter network cannot use it. Before Windows Server 2012, someone had to renew these certificates by hand, and forgotten renewals led to outages.

### What key-based renewal does

Key-based renewal builds on the Certificate Enrollment Web Services (CEP and CES) covered in Module 04. It lets a client renew its certificate automatically, using the key of its existing certificate to authenticate. In effect: "I already hold a valid certificate from you, so you can trust my renewal request." The client does not need a domain account or a password for renewals.

### How it works

1. The computer enrolls for the first time through CES. This uses an authentication method such as username and password (or Kerberos for a domain account), so the initial identity is verified.
2. As the certificate nears the end of its life, the computer's autoenrollment contacts a second CEP/CES instance that is set up for certificate authentication and renewal-only mode.
3. The computer proves who it is by using its existing valid certificate, and the CA issues the renewed certificate through the same web service channel.
4. The new certificate is installed, and the process repeats before the next expiry.

### Setup overview

The full procedure is in Microsoft's guide on certificate key-based renewal, and a short summary is:

- Install CEP and CES on a server that is domain-joined. Both services require HTTPS, so the server needs a valid TLS certificate.
- Configure one pair of CEP and CES instances for the initial enrollment (username and password, or Kerberos). Do not tick the key-based renewal option on this pair.
- Configure a second pair with client certificate authentication, with key-based renewal enabled. In PowerShell, the `Install-AdcsEnrollmentPolicyWebService` cmdlet has a `-KeyBasedRenewal` switch, and `Install-AdcsEnrollmentWebService` has `-RenewalOnly` and `-AllowKeyBasedRenewal`.
- In this mode, the policy service returns only templates that are set for key-based renewal, and it does not accept requests for new certificates.
- Configure the certificate template to allow key-based renewal, and make sure the clients are set to use the CEP URLs through Group Policy or local policy (*Certificate Services Client - Certificate Enrollment Policy*).
- The two pairs of services can run on the same server, using different virtual application names or ports.

### Benefits and limits

| Benefits | Limits and things to watch |
|---|---|
| Automatic renewal for non-domain and cross-forest computers | The existing certificate must still be valid when renewal is attempted, so renewal must happen before expiry. If it has already expired, the client must enroll again. |
| No manual work and fewer expiry outages | Needs HTTPS, correct DNS and firewall access to the CEP and CES endpoints. |
| Renewal-only mode means the CES account does not need delegation rights for renewals | Only works for templates that are configured for key-based renewal. |
| Works together with CEP and CES for the first enrollment | The initial enrollment still needs a separate, secure method (for example username and password). |

### Security points

- Always use HTTPS on CEP and CES, and protect the web servers as you would any server that can request certificates (see the ESC8 note in Module 04).
- Limit which templates allow key-based renewal and who can enroll for them.
- Keep renewal periods long enough, so a failed renewal is noticed and repaired before the certificate expires.
- Monitor the CES server and the CA for failed renewal requests.

### How it compares with other methods

| Scenario | Method |
|---|---|
| Domain-joined computer | Autoenrollment through Active Directory |
| Non-domain computer, first enrollment | CEP and CES with username and password |
| Non-domain computer, renewal | Key-based renewal through CEP and CES |
| Network or mobile device | NDES with SCEP or an Intune profile |

## Module Review

- The classic features in this module (site awareness, IDN, certificate lifecycle notifications, key-based renewal) were introduced in Windows Server 2012 and 2012 R2 and are fully supported on Windows Server 2025.
- **Site awareness** lets clients choose the CA with the lowest AD site link cost. It uses the `msPKI-Site-Name` attribute on the CA object, set with `certutil -setcasites`. Windows 8 and later clients support it by default, and CAs with the same cost are chosen randomly to spread the load.
- **IDN support** allows non-ASCII (punycode) names in enrollment, certreq requests, CRL and OCSP publishing, and the certificate user interfaces.
- **Certificate lifecycle notifications** (CLM in this module) raise events for new, renewed, replaced, expiring, expired, deleted, archived and exported certificates, so scripts can react and administrators are warned before expiry.
- **Key-based renewal** lets computers outside the domain renew automatically, using their existing valid certificate to authenticate through CEP and CES in renewal-only mode over HTTPS.
- **Partitioned CRLs** (October 2025 update, also available on Windows Server 2019 and 2022) split a large CRL into smaller ones, with each certificate's CDP pointing to its own partition. No client changes are needed, but LDAP CDP URLs are not supported and the feature should be lab-tested first.
- **Larger extension limit** (4 KB limit removed) and **expanded audit events 4886 to 4889** (new fields such as SAN, template, authentication service and DCOM or RPC) support complex certificates, post-quantum data and better SIEM detection.
- **ML-DSA post-quantum signatures** are supported in AD CS on Windows Server 2025 only, from the May 2026 update (KB5087539). ML-KEM and composite algorithms are planned, and no backport to 2019 or 2022 is expected.
- **Hardening and upgrade:** use HTTPS and Extended Protection on web enrollment endpoints, HSM-backed keys, tight template permissions, a full CA backup before any upgrade, and the same CDP and AIA aliases after a migration.

## Common Interview Questions

**What is AD CS site awareness and why use it?**
It lets clients enroll through the CA with the lowest AD site cost, usually the one in their own site. This improves speed, reduces WAN use and gives failover to the next closest CA.

**How do you enable site awareness?**
Populate the `msPKI-Site-Name` attribute on each Enterprise CA object with `certutil -setcasites`. Windows 8 and later clients need no configuration.

**What happens if a CA has no site name set?**
It is given the highest cost and is tried last.

**What is key-based renewal?**
A feature that lets a client renew a certificate by authenticating with its existing certificate through CEP and CES, without a domain account. It is mainly for non-domain and cross-forest computers.

**Why does key-based renewal need two CEP/CES configurations?**
One handles the initial enrollment with username and password or Kerberos. The other runs in renewal-only mode with certificate authentication.

**What if the certificate has already expired?**
Key-based renewal cannot be used, and the client must enroll again with its initial authentication method.

**What are IDNs and how are they stored in certificates?**
Domain names with non-ASCII characters. They are stored in the ASCII punycode form.

**What do certificate lifecycle notifications give you?**
Events for key points in a certificate's life, which can trigger scripts or alerts, for example before expiry or after renewal.

**What is a partitioned CRL and what problem does it solve?**
It splits a very large CRL into many smaller ones. Each certificate is assigned a partition at issuance and its CDP points to that partition's CRL, so clients download a small file and need no changes.

**What is the main design restriction for partitioned CRLs?**
They need HTTP CDP locations. LDAP CDP URLs are not supported, so remove them before enabling the feature.

**Which Windows Server versions get partitioned CRLs?**
Windows Server 2019, 2022 and 2025, through the October 2025 updates.

**What changed in AD CS audit logging?**
Events 4886 to 4889 gained fields such as the subject and SAN from the CSR, the requested template, authentication service and level, and whether the request used DCOM or RPC, which helps detect template abuse.

**Does AD CS on Windows Server 2025 support post-quantum certificates?**
Yes for signatures. ML-DSA-44, 65 and 87 are supported from the May 2026 update (KB5087539), on Windows Server 2025 only. ML-KEM and composite algorithms are planned.

**Are the site awareness, IDN and key-based renewal features new in Windows Server 2025?**
No. They were introduced in Windows Server 2012 and 2012 R2 and are still supported. The new 2025-era features are partitioned CRLs, larger extensions, richer audit events and ML-DSA.

**How would you move an AD CS server from 2022 to 2025?**
Take a full CA backup and test a restore, then do an in-place upgrade or a migration while keeping the CA name and the CDP and AIA aliases. Apply the latest updates, test new features one at a time in a lab, and update monitoring and HSM drivers.
