# Certificate Revocation and Chain Building

We saw that a certificate is a public key bound to an identity and signed by a CA. That alone is not enough for a client to accept it. The client has to answer two separate questions every time it sees a certificate:

- **Do I trust it?** This is answered by chain building: can the certificate be linked, through signatures, to a CA that I already trust?
- **Is it still good?** This is answered by revocation checking: has the CA cancelled this certificate before its expiry date?

This module covers both, plus the design and troubleshooting work that a PKI administrator does around them. It is split into these topics:

- **Introduction** - why revocation matters and how the pieces fit
- **Certificate Revocation and Chain Building** - CRLs, delta CRLs and how a client builds and validates a chain
- **Designing and Configuring CDP Locations** - CDP and AIA extensions, URL design and publishing settings
- **Revocation Cache** - how Windows caches CRLs, OCSP responses and CA certificates
- **OCSP** - the Online Responder and real-time status checking
- **Troubleshooting Revocation** - tools, error codes and a step-by-step method
- **Module Recap**

## Introduction

### Why certificates need to be revoked

A certificate normally stays valid until its expiry date, which can be one or two years away or much longer for CA certificates. Many things can go wrong before that date, so PKI needs a way to withdraw trust early. Common reasons are:

- **Key compromise** - the private key was stolen or exposed.
- **CA compromise** - the issuing CA itself was compromised.
- **Affiliation changed** - the user left the company or the device was retired.
- **Superseded** - a new certificate replaced the old one.
- **Cessation of operation** - the service is shut down.
- **Certificate hold** - a temporary suspension, which can later be released (the only reason that is reversible).

Revocation is recorded by the CA against the certificate serial number, along with the date and the reason code.

### How the pieces fit together

Two certificate extensions tell the client where to look. Both are added to a certificate when it is issued, so they must be correct before the CA starts issuing.

- **AIA (Authority Information Access)** - points to the issuer's own CA certificate (so the client can build the chain) and optionally to an OCSP responder.
- **CDP (CRL Distribution Point)** - points to the CRL published by the issuing CA.

The client uses AIA to find the parents, builds the chain up to a trusted root, and then uses CDP or OCSP to check whether each certificate in that chain has been revoked.

## Certificate Revocation and Chain Building

### Certificate Revocation List (CRL)

A CRL is a signed list of revoked certificates published by a CA at regular intervals. It is signed by the CA, so a client can trust it even if it is downloaded from an ordinary web server. A CRL contains:

- The **issuer** (the CA that signed the list)
- **This Update** and **Next Update** - the time the list was published and the time by which a newer list must be available
- The list of **revoked serial numbers**, each with a revocation date and reason code
- A **CRL Number** that increases with every publication
- The **Authority Key Identifier**, so the client can match the CRL to the right CA key

If the current time is past Next Update and no newer CRL can be downloaded, the CRL is treated as expired and the client cannot confirm the revocation status. In Windows this normally results in a revocation offline error and the certificate is rejected.

### Base CRL and Delta CRL

- **Base CRL** - the full list of all revoked certificates that have not yet expired. It can grow large in busy environments, which makes it slow to download and publish.
- **Delta CRL** - only the changes since the last base CRL. It is small, so it can be published more often (for example daily) while the base CRL is published less often (for example weekly).

A client that supports delta CRLs checks the base CRL first and then the delta CRL, using the Freshest CRL extension in the CRL to find the delta location. A certificate is treated as revoked if it appears in either one.

### Publication interval and overlap

- **Publication interval** - how often the CA publishes a new CRL. The CRL validity period equals this interval plus the overlap.
- **Overlap period** - extra time at the end of a CRL's life during which a new CRL is already available but the old one is still valid. This gives clients, caches and replication time to catch up before the old list expires. In Windows the overlap is configurable but limited to a maximum of 12 hours for either the CRL or the delta CRL.

Typical designs used in practice (adjust to your own policy):

| CA type | Base CRL | Delta CRL | Notes |
|---|---|---|---|
| Offline Root CA | 6 to 12 months | Not used | Few revocations. Must be powered on, published and copied to the web server before the CRL expires. |
| Online Issuing CA | 1 week | 1 day | Delta CRLs keep the base CRL small and revocation reasonably fresh. |

> The offline Root CA is the classic outage cause. If its CRL expires, every certificate chaining to it fails revocation, even though everything else is healthy.

### Revoking a certificate and publishing

Revoking a certificate in the CA console only records it in the CA database. Clients do not know until a new CRL is published. Publish a new CRL immediately after an urgent revocation, using the CA console or:

```
certutil -crl
```

Then confirm the new CRL is actually available at every HTTP and LDAP location. Remember that clients may still hold a cached copy (covered in the Revocation Cache topic).

### Chain building

Chain building is how a client turns a single end-entity certificate into a path of trust. Windows does this through CryptoAPI (the CAPI2 engine). The steps are:

1. Start with the end-entity certificate (for example a web server certificate).
2. Find the issuer. The client matches the certificate's Authority Key Identifier to the issuer's Subject Key Identifier, and checks the issuer name.
3. Look for the issuer certificate in the local stores first (Intermediate Certification Authorities and Trusted Root Certification Authorities). If it is not there, the client downloads it from the AIA URL in the certificate.
4. Repeat until the chain reaches a self-signed root that exists in the Trusted Root store.
5. Validate the chain (see below).

If the chain cannot reach a trusted root, the result is a chaining error. Two common ones are a certificate chain processed correctly but terminated in a root certificate which is not trusted (untrusted root) and a partial chain error, which usually means a missing intermediate certificate or an unreachable AIA location.

### Chain validation checks

Building the chain is only the start. For each certificate in the chain, the client also checks:

- **Signature** - each certificate is correctly signed by its issuer's public key.
- **Validity period** - not expired and not yet valid.
- **Basic Constraints** - the issuer is actually allowed to act as a CA, and path length limits are respected.
- **Key Usage and Enhanced Key Usage** - the certificate is allowed to be used for the intended purpose (for example Server Authentication).
- **Name constraints and policies** - if the CA certificates carry them, they are enforced (used in qualified subordination).
- **Revocation status** - checked for every certificate in the chain except the trusted root (a root is trusted by being installed, so it has no issuer to revoke it).

The whole chain fails if any one certificate fails. A broken CRL for the Root CA can therefore stop an end-entity certificate that was issued yesterday.

### Why a two-tier hierarchy affects revocation

In a typical enterprise design, the Root CA signs only the Issuing CA certificate, and the Issuing CA signs everything else. This means there are always two CRLs involved in a normal check: the Issuing CA's CRL (for the end-entity certificate) and the Root CA's CRL (for the Issuing CA certificate). Both CDP locations must be reachable and current.

## Designing and Configuring CDP Locations

### CDP and AIA in a nutshell

The CDP and AIA extensions on a CA are configured once, under **CA Properties > Extensions**. The settings apply to the certificates that CA issues from that point forward. Certificates already issued keep whatever was in them at the time, so this must be right before issuing begins.

- The **AIA** extension says where to find the up-to-date CA certificate (and optionally the OCSP responder).
- The **CDP** extension says where to find the up-to-date CRL signed by that CA.

### Types of locations

- **LDAP** - the CRL or CA certificate is published in Active Directory (the Configuration partition). Works for domain-joined clients inside the network. It is automatic for an Enterprise CA.
- **HTTP** - published on a web server (usually IIS). Works for any client, internal or external, including non-Windows devices.
- **File (local path)** - the local folder where the CA writes the CRL. This is for publishing only and is not included in issued certificates. Do not remove it, because the CA needs it.

### Design best practices

- **Always provide an HTTP location.** Domain-joined and non-domain, Windows and non-Windows clients can all use it. Many organisations use only HTTP.
- If you also publish via LDAP, place the HTTP URL after LDAP or according to your client mix, and make sure the first URL a client tries is the one most likely to work for it.
- **Use a DNS alias**, such as `pki.contoso.com`, instead of the CA server's own name. The CA can then be rebuilt or the web server moved without breaking every issued certificate.
- **Host the CRL on a separate web server** (not the CA itself) and put it behind a load balancer or a highly available setup if it is business critical. If the CDP is down, revocation checks fail across the organisation.
- **Keep it plain HTTP, not HTTPS.** Revocation data is already signed, and using HTTPS would require a certificate check to download the CRL that is used to check certificates, which creates a loop.
- **Offline Root CA:** publish CRLs to the local path and HTTP only, do not publish delta CRLs, and manually copy the CRL and CA certificate files to the web server after each publication.
- **Online Issuing CA:** enable delta CRLs (even if you start with them off, enabling them keeps the option open) and publish to both the local path and the web server.
- For external or internet-facing use, **avoid LDAP URLs**, because outside clients cannot reach Active Directory.

### Variables used in URLs

The CA console and certutil use variables so a single entry works for any CA name or suffix. The most common ones are:

| Variable | Meaning |
|---|---|
| `%1` | Server DNS name |
| `%2` | Server short name |
| `%3` | CA name |
| `%4` | Certificate name (the CA certificate suffix, for AIA) |
| `%6` | Configuration naming context DN (for LDAP) |
| `%7` | CA truncated name |
| `%8` | CRL name suffix (changes after the CA certificate is renewed with a new key) |
| `%9` | Delta CRL allowed (adds a plus sign to the delta CRL file name) |
| `%10` | CDP object class (for LDAP) |
| `%11` | CA object class (for LDAP) |

A typical HTTP CDP entry looks like this:

```
http://pki.contoso.com/pki/%3%8%9.crl
```

### CDP checkbox options and their flag values

In the Extensions tab, each CDP location has checkboxes. When you configure through certutil, they become numeric flags that add together.

| Option in the console | Flag |
|---|---|
| Publish CRLs to this location | 1 |
| Include in the CDP extension of issued certificates | 2 |
| Include in CRLs. Clients use this to find Delta CRL locations | 4 |
| Include in the IDP extension of issued CRLs | 8 |
| Publish Delta CRLs to this location | 64 |

Examples of what the numbers mean:

- `1` = only write the CRL to this place (a local path or share).
- `2` = include this URL in issued certificates (an HTTP URL on a web server that you copy files to yourself).
- `65` = publish the base CRL and the delta CRL to this path.
- `6` = include in issued certificates and in the CRLs for delta lookup.

AIA works the same way: `1` publishes the CA certificate to the location, `2` includes it in the AIA extension of issued certificates, and `32` includes the URL in the OCSP extension.

### Configuring with certutil

The console is fine for a single CA, but certutil is repeatable and good for documentation. Example for a Root CA:

```
certutil -setreg CA\CRLPublicationURLs "1:C:\Windows\System32\CertSrv\CertEnroll\%3%8%9.crl\n2:http://pki.contoso.com/pki/%3%8%9.crl"
certutil -setreg CA\CACertPublicationURLs "1:C:\Windows\System32\CertSrv\CertEnroll\%1_%3%4.crt\n2:http://pki.contoso.com/pki/%1_%3%4.crt"
```

CRL period settings:

```
certutil -setreg CA\CRLPeriodUnits 26
certutil -setreg CA\CRLPeriod Weeks
```

You can read the current values at any time with `certutil -getreg CA\CRLPublicationURLs`.

After changing the settings, restart the CA service and publish a new CRL:

```
net stop certsvc && net start certsvc
certutil -crl
```

### Web server notes (IIS)

- Create a virtual directory (for example `/pki`) and copy the `.crl` and `.crt` files there. Make sure the CA computer account has write permission if you publish to it automatically.
- If you publish delta CRLs over HTTP, the file name contains a plus sign. IIS blocks this by default, so **enable double escaping** on the virtual directory (`allowDoubleEscaping`), otherwise clients get a 404 for the delta CRL while the base CRL works fine.
- **Allow anonymous access** to the folder. Revocation checks run as many different accounts, including computers and services.
- Check firewalls, proxies and any CDN in front of the site. A CDN or proxy that caches old copies of a CRL can make it look expired.

## Revocation Cache

### Why caching exists

Checking revocation on every connection would be very slow and would flood the CDP server. To avoid this, Windows (CryptoAPI) caches the revocation data and CA certificates that it downloads. This is good for performance, but it is the main reason revocation behaviour sometimes looks inconsistent.

### Where the cache lives

- **In memory, per process** - a running application keeps what it already fetched. Clearing disk caches will not change what that process already holds. Restarting the process does.
- **On disk, per user and per service account** - in the `CryptnetUrlCache` folder. Each profile has its own copy.

| Account | Cache location |
|---|---|
| Logged-on user | `%USERPROFILE%\AppData\LocalLow\Microsoft\CryptnetUrlCache` |
| Local System | `%windir%\System32\config\systemprofile\AppData\LocalLow\Microsoft\CryptnetUrlCache` |
| Local Service and Network Service | `%windir%\ServiceProfiles\<account>\AppData\LocalLow\Microsoft\CryptnetUrlCache` |

Each folder has a `Content` subfolder (the downloaded files) and a `MetaData` subfolder (information about each entry).

### How long cached data is used

A cached CRL is used until its Next Update time (or the overlap logic and any configured freshness limit says otherwise). A cached OCSP response is used until its own validity period ends. This means:

- If you revoke a certificate and publish a new CRL, a client with an unexpired cached CRL will not see the revocation until the old CRL expires or the cache is cleared.
- This is why short CRL lifetimes, delta CRLs and OCSP exist: they narrow the window during which a revoked certificate is still accepted.

### Viewing and clearing the cache

| Task | Command |
|---|---|
| List cached CRL entries | `certutil -urlcache CRL` |
| List all cached entries | `certutil -urlcache *` |
| Delete all cached entries for the current user | `certutil -urlcache * delete` |
| Delete cached CRLs only | `certutil -urlcache CRL delete` |
| Delete cached data for the machine (run elevated as SYSTEM, or clear the folders above) | use `PsExec -s` with the same command |

These commands only act on the current user's disk cache. To clear the cache for services you need to run the command as that account or delete the contents of the relevant `CryptnetUrlCache` folders. For an application that is still running, restart it as well, because of the in-memory cache.

The cache also holds Certificate Trust Lists (CTLs). Stale entries there are the cause of Application log warnings from CAPI2 such as event IDs 4107 and 11, which are fixed by clearing the cache.

### Practical tips

- When testing a fix, **always clear the cache first**, otherwise you may be testing old data.
- Test as the **same account that fails** (a user, SYSTEM or a service account), because each has its own cache and its own network access.
- Do not use cache clearing as the fix on its own. If the cause is an unreachable CDP or an expired CRL, the problem returns as soon as the cache is refilled.

## OCSP

### The problem OCSP solves

CRLs have two weaknesses. They can become large, and they are only as fresh as the last publication. Online Certificate Status Protocol (OCSP) lets the client ask a server about one certificate, and the response size is small and constant no matter how many certificates have been revoked.

### How OCSP works

1. The client reads the OCSP URL from the certificate's AIA extension.
2. It sends a request to the responder containing the issuer details and the certificate's serial number.
3. The responder returns a signed response with one of three statuses:
   - **Good** - the certificate is not revoked.
   - **Revoked** - includes the revocation time and reason.
   - **Unknown** - the responder does not know this certificate or issuer.
4. The client validates the signature on the response and the responder's signing certificate, and then caches the answer until its validity ends.

OCSP uses plain HTTP, for the same reason as CRLs. Windows will normally try OCSP first when an OCSP URL is present in the certificate, and fall back to the CRL if OCSP does not work.

### Microsoft Online Responder

In Windows Server, OCSP is provided by the Online Responder role service of AD CS. Important points:

- The responder **does not talk to the CA database**. It reads the CA's CRLs (base and delta) from the CDP locations and builds responses from them. If the CRL is stale, the OCSP answers are stale too. OCSP does not replace CRL publishing; it sits on top of it.
- It needs a **signing certificate**, issued from the **OCSP Response Signing** template. This certificate is short-lived and should be set to auto-enroll and auto-renew. It carries the OCSP No Revocation Checking extension so clients do not need to check revocation of the signer itself.
- The CA must be configured to publish the OCSP URL in the AIA extension of issued certificates (the *Include in the online certificate status protocol (OCSP) extension* option, flag 32). Certificates issued before this setting was added will not contain the URL.
- A **revocation configuration** is created for each CA that the responder serves. It defines the CA certificate, the signing certificate and the location of the CRLs.
- Several responders can be grouped into an **Online Responder Array** for scale and availability, managed from the Online Responder console (`ocsp.msc`), which also shows the status of each revocation configuration and has a *Refresh Revocation Data* action.

### Setup summary

1. Install the Online Responder role service on a server (usually separate from the CA).
2. On the issuing CA, create and publish the OCSP Response Signing template and give the responder computer enroll and autoenroll permission.
3. Add the OCSP URL to the CA's AIA extension and restart the CA service. Re-issue certificates that need it.
4. In `ocsp.msc`, add a Revocation Configuration, choose the CA certificate, and let it enrol the signing certificate automatically.
5. Check that the configuration status is working and the signing certificate is OK.

### CRL versus OCSP

| Point | CRL | OCSP |
|---|---|---|
| What is returned | Entire list of revoked certificates | Status of a single certificate |
| Size | Grows with revocations | Small and constant |
| Freshness | Only as new as the last publication | Depends on how fresh the responder's CRL data is; can be more current |
| Offline use | Can be cached and used for days | Usually needs a live responder |
| Extra infrastructure | Web server | Online Responder server and signing certificate |
| Privacy | Client does not reveal which certificate it is checking | The responder learns which certificate is being checked |

Most enterprise designs publish both: OCSP for speed and freshness, CRL as the fallback.

### OCSP stapling

With OCSP stapling, the web server fetches a signed OCSP response itself and sends it with the TLS handshake. The client no longer needs to contact the responder, which improves speed and privacy. This is a server-side feature of products such as IIS and many web servers, mentioned here because it often appears in discussions of revocation performance.

## Troubleshooting Revocation

### Common errors

| Error | Code | Usual meaning |
|---|---|---|
| CRYPT_E_REVOKED | 0x80092010 | The certificate really is revoked (or a stale/incorrect CRL says so). |
| CRYPT_E_NO_REVOCATION_CHECK | 0x80092012 | The client could not check revocation, often because the certificate has no CDP or AIA OCSP entry. |
| CRYPT_E_REVOCATION_OFFLINE | 0x80092013 | The revocation server could not be reached, or the CRL has expired. This is the most common one. |
| CERT_E_UNTRUSTEDROOT | 0x800B0109 | The chain ends at a root that is not in the Trusted Root store. |
| CERT_E_CHAINING | 0x800B010A | A partial chain: a parent certificate is missing or cannot be downloaded. |
| CERT_E_EXPIRED | 0x800B0101 | A certificate in the chain has expired. |

Note that *revocation offline* does not always mean the server is down. It also appears when the CRL is reachable but already expired, when the download is blocked by a proxy, or when a CDN returns an old copy.

### A step-by-step method

**1. Reproduce with certutil.** Export the failing certificate and run:

```
certutil -urlfetch -verify certificate.cer
```

This forces Windows to download the chain and revocation data and prints the result for every certificate in the chain, including which URL worked and which failed.

**2. Use the URL Retrieval Tool.** `certutil -URL certificate.cer` opens a window that tests each AIA, CDP and OCSP URL separately, with and without cache.

**3. Check the CRL itself.** Download it and look at the dates:

```
certutil -dump issuingca.crl
```

If Next Update is in the past, the CRL has expired. Publish a new one on the CA (or, for an offline root, power it up, run `certutil -crl`, and copy the new file to the web server).

**4. Test every URL in the certificate.** Open the CDP and AIA URLs from the failing machine and, if possible, from the same network segment and account. Confirm the HTTP location returns 200, including the delta CRL with its plus sign. Check DNS, firewall, proxy and load balancer behaviour.

**5. Check what the certificate actually contains.** Open it and look at the CRL Distribution Points and Authority Information Access fields. If the URLs are wrong or missing, the certificate was issued before the CA was configured correctly and needs to be re-issued after the fix.

**6. Check the CA and responder.**

- On the CA, confirm the CRL publication paths and CRL period with `certutil -getreg CA\CRLPublicationURLs` and look in the Application log for publishing failures.
- Use `PKIView.msc` (Enterprise PKI) on a domain-joined machine. It shows each CA and the health of its CDP and AIA locations with clear status values such as OK, unable to download or expired.
- On the Online Responder, open `ocsp.msc` and check the revocation configuration status, the signing certificate expiry, and refresh the revocation data. The responder's event log shows failures to retrieve CRLs or an expired signing certificate.

**7. Use the CAPI2 log when the cause is still not clear.** Enable it in Event Viewer under *Applications and Services Logs > Microsoft > Windows > CAPI2 > Operational*. The Build Chain (event 11) and Verify Revocation (event 41) entries show the exact certificate, URL and error for each failure.

**8. Clear the cache and test again.** Clear the user and service caches as described earlier, restart the application, and re-test.

### Frequent causes (quick checklist)

- The offline Root CA CRL has expired, because nobody renewed and copied it.
- The CRL was published to the CA's local folder but never copied to the web server, or the replication to AD (for LDAP) is late.
- The certificate was issued before the CDP, AIA or OCSP URL was added.
- The CRL name changed after the CA certificate was renewed with a new key (the `%8` suffix, for example `CAName(1).crl`), but the web server or the certificates still point to the old name.
- Delta CRL returns 404 because double escaping is not enabled in IIS.
- The DNS name, firewall rule or proxy blocks the CDP, or a CDN/proxy cache serves an old CRL.
- LDAP-only CDP used by a non-domain or external client.
- The OCSP signing certificate has expired or the responder cannot download the CRL.
- Clock skew between client and CA, which makes a valid CRL look not yet valid or already expired.
- A missing intermediate certificate and no working AIA URL, so the chain cannot be built.
- A stale cache holds a bad or old result even though the underlying problem has been fixed.

## Recap

- Every certificate check has two parts: **chain building** (trust) and **revocation checking** (still valid).
- A **CRL** is a signed list of revoked serial numbers with a Next Update time. A **delta CRL** carries only the changes since the last base CRL.
- The **overlap period** keeps a valid CRL available while the next one is distributed. The maximum is 12 hours.
- Chain building uses AKI/SKI matching, local stores and the AIA extension, and ends at a trusted root. Revocation is checked for every certificate except the root.
- The **CDP** points to CRLs and the **AIA** points to CA certificates and OCSP. They are written into certificates at issuance, so configure them before the CA issues anything.
- Use a DNS alias on HTTP for CDP and AIA, keep the local path, avoid delta CRLs on the offline root, and enable double escaping for delta CRLs on IIS.
- Windows caches revocation data in memory per process and on disk in `CryptnetUrlCache`, and uses a CRL until its Next Update. Clear with `certutil -urlcache * delete` and restart the application.
- **OCSP** answers for one certificate at a time with a signed Good, Revoked or Unknown. The Microsoft Online Responder builds its answers from the CA's CRLs and needs an OCSP Response Signing certificate.
- Troubleshoot with `certutil -urlfetch -verify`, `certutil -URL`, `certutil -dump`, `PKIView.msc`, `ocsp.msc` and the CAPI2 operational log.

## Common Interview Questions

**What is the difference between a base CRL and a delta CRL?**
The base CRL lists all revoked certificates. The delta CRL lists only the changes since the last base CRL, so it is smaller and can be published more often.

**What are CDP and AIA used for?**
CDP tells clients where to download the CRL. AIA tells clients where to download the issuer's CA certificate and where the OCSP responder is.

**Why not use HTTPS for a CDP?**
The CRL is already signed. HTTPS would require a certificate check to download the data needed to do certificate checks, which creates a circular dependency.

**Why do we not publish delta CRLs from an offline root?**
The root revokes very few certificates, so a delta CRL is rarely needed and an offline server cannot publish it automatically anyway.

**A certificate was revoked but a client still accepts it. Why?**
The client is probably using a cached CRL or OCSP response that has not expired yet. Publish a new CRL, and clear the cache or wait for the old data to expire.

**Users report a revocation offline error for everything issued by the Issuing CA. Where do you start?**
Run `certutil -urlfetch -verify` on a certificate, find which URL fails, then check the CRL dates for both the Issuing CA and the Root CA. An expired offline root CRL is a very common cause.

**How does OCSP relate to CRLs in Microsoft AD CS?**
The Online Responder reads the CA's CRLs and answers per-certificate queries from that data. It depends on the CRLs being published on time.

**What does the OCSP Response Signing certificate do?**
It is the certificate whose private key signs OCSP responses, so clients can trust the answers. It is short-lived and should auto-renew.

**Why did the CRL name change after the CA certificate was renewed?**
When the CA certificate is renewed with a new key, the CRL name suffix (`%8`) is added to the file name, for example `CAName(1).crl`. The CDP URL variable must include `%8` so that clients find the right file.
