# Introduction to PKI

This module builds the foundation for everything that follows in PKI. Before looking at Certificate Authorities, templates, CRLs or OCSP, it is important to understand the cryptography that a Public Key Infrastructure is built on. A PKI is basically a system that manages keys and certificates so that encryption, hashing and digital signatures can be trusted at scale.

The module is split into four topics:

- **Introduction** - what PKI is and what problems it solves
- **Introduction to Cryptography** - the goals and building blocks of cryptography
- **Encryption** - symmetric and asymmetric encryption, and how they work together
- **Hash Functions and Digital Signatures** - integrity, authentication and non-repudiation

---

## Introduction

### What is PKI?

Public Key Infrastructure (PKI) is the set of people, policies, processes, hardware and software used to create, issue, manage, distribute, use, store and revoke digital certificates and public keys. A digital certificate is what links a public key to an identity such as a user, a computer, a web server or a network device.

The key point is that PKI does not invent new cryptography. It takes the cryptography covered in this module and adds trust on top of it.

### The problem PKI solves

Public key cryptography lets two parties communicate securely without sharing a secret first. But it creates a new question: how do I know this public key really belongs to the person or server I think it does?

If an attacker can swap a public key with their own, they can read or modify everything. PKI answers this by having a trusted third party, the Certificate Authority (CA), digitally sign a certificate that says "this public key belongs to this identity". Anyone who trusts the CA can then trust the certificate.

### Main components of a PKI

- **Certificate Authority (CA)** - issues and signs certificates. In a typical enterprise this is a two-tier hierarchy: an offline Root CA and one or more online Issuing (Subordinate) CAs.
- **Registration Authority (RA)** - verifies the identity of the requester before a certificate is issued. In Microsoft AD CS, this role is often handled by the CA and certificate templates together with Active Directory.
- **Certificate** - an X.509 file that contains the subject, the public key, the validity period, the issuer, and the issuer's signature.
- **Certificate Revocation** - a way to cancel trust before expiry, using CRLs (Certificate Revocation Lists) or OCSP (Online Certificate Status Protocol).
- **Certificate Repository / Distribution Points** - where certificates, CRLs and CA information are published (AIA and CDP locations).
- **Clients and end entities** - users, devices, servers and applications that request and use certificates.
- **Key storage** - where private keys live: software storage, TPM, smart card or HSM (Hardware Security Module).

### Where PKI is used

- HTTPS / TLS for websites and internal applications
- Wi-Fi and VPN authentication (802.1X, certificate-based)
- Smart card and user logon
- Device identity for MDM and endpoint management (for example Intune with SCEP or PKCS)
- Email signing and encryption (S/MIME)
- Code signing and document signing
- Network devices (switches, routers, firewalls) through NDES / SCEP

## Introduction to Cryptography

### What is cryptography?

Cryptography is the practice of protecting information by transforming it so that only the intended parties can read it or verify it. The word comes from Greek roots meaning "hidden writing". Modern cryptography is mathematics applied to security, and it is used far beyond secrecy.

### Basic terms

- **Plaintext** - the original readable data.
- **Ciphertext** - the unreadable data produced after encryption.
- **Encryption** - converting plaintext into ciphertext using an algorithm and a key.
- **Decryption** - converting ciphertext back into plaintext.
- **Algorithm (cipher)** - the mathematical procedure used.
- **Key** - the secret (or public/private) value that controls the output of the algorithm.
- **Key length** - the size of the key in bits. Longer keys generally mean more work for an attacker.

A core principle, known as **Kerckhoffs's principle**, says that a system should stay secure even if everything about it is public except the key. This is why modern algorithms such as AES and RSA are openly published and tested, and why protecting the key is the most important job.

### Security goals of cryptography

Cryptography is usually described using the following goals:

- **Confidentiality** - only authorised parties can read the data. Provided by encryption.
- **Integrity** - the data has not been changed. Provided by hash functions and signatures.
- **Authentication** - the sender or system is who it claims to be. Provided by digital signatures and certificates.
- **Non-repudiation** - the sender cannot later deny having sent or signed something. Provided by digital signatures.

These goals are often shortened to the CIA triad (confidentiality, integrity, availability), with authentication and non-repudiation added on top for PKI discussions.

### The three building blocks

| Building block | What it does | Main goal |
|---|---|---|
| Symmetric encryption | Encrypts and decrypts with the same key | Confidentiality |
| Asymmetric encryption | Uses a public and private key pair | Key exchange, authentication, signatures |
| Hash functions | Creates a fixed-size fingerprint of data | Integrity |

PKI combines all three. Certificates use asymmetric keys, signatures use hashes plus asymmetric keys, and the actual data in a TLS session is protected with symmetric encryption.

## Encryption

### Symmetric encryption

Symmetric encryption uses one shared secret key for both encryption and decryption. Both sides must have the same key before they can communicate.

- **Common algorithms** - AES (128, 192 and 256 bit keys), ChaCha20. Older ones such as DES and 3DES are considered weak or deprecated.
- **Strengths** - very fast and efficient, so it is the right choice for large amounts of data such as files, disks, databases, backups and VPN tunnels.
- **Weakness** - the key distribution problem. If two people need to share a key, they must find a safe way to send it. If you have many parties, the number of keys needed grows quickly.

AES (Advanced Encryption Standard) is the dominant symmetric cipher today. It is a NIST standard and AES-256 is commonly recommended where high security is needed. AES is a block cipher, and it is normally used in a mode such as GCM, which provides both encryption and integrity checking.

### Asymmetric encryption (public key cryptography)

Asymmetric encryption uses a mathematically linked pair of keys:

- **Public key** - can be shared with anyone.
- **Private key** - must be kept secret by the owner.

What one key does, only the other key can undo. This gives two different uses:

- **Encrypting for confidentiality** - encrypt with the receiver's public key. Only the receiver's private key can decrypt it.
- **Signing for authenticity** - sign with the sender's private key. Anyone can verify it with the sender's public key.

#### Common algorithms

- **RSA** - based on the difficulty of factoring large numbers. 2048-bit is the minimum commonly accepted today, and 3072 or 4096 bit is used for higher security and long-lived keys such as Root CAs.
- **ECC (Elliptic Curve Cryptography)** - gives similar security with much smaller keys (for example a 256-bit ECC key is roughly comparable to a 3072-bit RSA key). Examples are ECDSA and ECDH.
- **Diffie-Hellman (DH / ECDH)** - not used to encrypt data directly, but lets two parties agree on a shared secret over an open network.

#### Strengths and weaknesses

- Solves the key distribution problem, because the public key can be shared openly and each entity only needs one key pair.
- Much slower than symmetric encryption, so it is not suitable for encrypting large data.

### Symmetric vs asymmetric at a glance

| Point | Symmetric | Asymmetric |
|---|---|---|
| Keys | One shared secret key | Public key + private key |
| Speed | Fast | Slow |
| Typical key size | 128 / 256 bit (AES) | 2048+ bit (RSA), 256 bit (ECC) |
| Best for | Bulk data encryption | Key exchange, certificates, signatures |
| Main problem | Sharing the key safely | Performance |
| Examples | AES, ChaCha20 | RSA, ECC, Diffie-Hellman |

### Hybrid encryption - how both work together

Real systems do not choose one or the other. They use asymmetric cryptography to safely set up a key, and symmetric cryptography to protect the data. This is called hybrid encryption, and it is how HTTPS, S/MIME and most secure protocols work.

A simple example of sending an encrypted message from Alice to Bob:

1. Alice generates a random symmetric key (a session key).
2. Alice encrypts the message with that session key using AES.
3. Alice encrypts the session key with Bob's public key.
4. Alice sends both the encrypted message and the encrypted session key.
5. Bob uses his private key to recover the session key.
6. Bob uses the session key to decrypt the message.

In modern TLS, the session key is usually agreed using an ephemeral Diffie-Hellman exchange (ECDHE), and the server's certificate and signature prove that the server is genuine. This also provides **forward secrecy**, meaning that even if the server's private key leaks later, old recorded sessions cannot be decrypted.

### Why this matters for PKI

Encryption alone does not tell you who you are talking to. If Alice encrypts to "Bob's public key" but the key actually belongs to an attacker, the encryption is useless. This is the gap that certificates and CAs fill.

### Key size and quantum note

Symmetric keys are considered more resistant to future quantum computers than RSA and ECC. A large quantum computer could break RSA and ECC using Shor's algorithm, which is why the industry is moving toward post-quantum cryptography (PQC). For symmetric encryption, doubling the key size (for example using AES-256) is the usual answer. This is covered in more depth in later modules.

## Hash Functions and Digital Signatures

### What is a hash function?

A cryptographic hash function takes input of any size and produces a fixed-size output, called a hash, digest or fingerprint. For example, SHA-256 always produces 256 bits whether the input is one word or an entire book.

A hash is not encryption. There is no key and it is not meant to be reversed. It is a one-way fingerprint.

### Properties of a good cryptographic hash

- **Deterministic** - the same input always gives the same hash.
- **Fast to compute** - a hash can be produced quickly for any input.
- **Fixed-length output** - regardless of input size.
- **Pre-image resistance (one-way)** - given a hash, it must be infeasible to find an input that produces it.
- **Second pre-image resistance** - given one input, it must be infeasible to find a different input with the same hash.
- **Collision resistance** - it must be infeasible to find any two different inputs that produce the same hash.
- **Avalanche effect** - changing even one bit of the input changes the output completely and unpredictably.

### Collisions

Since there are infinite possible inputs and only a limited number of outputs, collisions must exist in theory. The goal is that finding one is practically impossible. Because of the birthday paradox, the effort needed to find a collision is roughly 2 to the power of half the hash length. For SHA-256 this is around 2^128 operations, which is not feasible with any known technology.

### Common hash algorithms

| Algorithm | Output size | Status |
|---|---|---|
| MD5 | 128 bit | Broken. Do not use for security. |
| SHA-1 | 160 bit | Collision resistance broken (the 2017 SHAttered attack). Deprecated for certificates. |
| SHA-2 (SHA-256, SHA-384, SHA-512) | 224 to 512 bit | Current standard. SHA-256 is the most widely used. |
| SHA-3 | 224 to 512 bit | Standardised in 2015. Different internal design from SHA-2, available as an alternative. |

This is the reason many organisations ran SHA-1 to SHA-2 migration projects for their CAs and certificates. Browsers and operating systems stopped trusting SHA-1 signed certificates.

### What hashes are used for

- **File integrity** - software vendors publish the SHA-256 of a download so you can compare it with the hash of your copy.
- **Digital signatures** - the hash of the data is what actually gets signed.
- **Certificate thumbprints** - the thumbprint you see on a certificate is a hash of the certificate, used to identify it uniquely.
- **Password storage** - passwords are stored as salted hashes. For this purpose, slow purpose-built algorithms such as bcrypt or Argon2 are used rather than plain SHA-256.
- **Message authentication (HMAC)** - a hash combined with a secret key, used to prove both integrity and that the sender knows the key.

### What is a digital signature?

A digital signature is the electronic equivalent of a handwritten signature, but stronger. It proves three things:

- **Authenticity** - the data came from the owner of the private key.
- **Integrity** - the data has not been changed since it was signed.
- **Non-repudiation** - the signer cannot credibly deny signing it.

Only the owner of the private key can create the signature, but anyone with the public key can verify it.

### How a digital signature works

**Signing (sender)**

1. The sender calculates the hash of the message or document (for example SHA-256).
2. The sender encrypts (signs) that hash using their private key.
3. The result is the digital signature, which is sent along with the message and the sender's certificate.

**Verifying (receiver)**

1. The receiver calculates the hash of the received message.
2. The receiver uses the sender's public key to decrypt the signature and recover the original hash.
3. If both hashes match, the message is authentic and unchanged. If not, the data was modified or the signature is not valid.

Signing the hash instead of the full message is done for speed, because asymmetric operations are slow and a hash is small and fixed in size.

Common signature algorithms are RSA with SHA-256 (RSASSA-PKCS1-v1_5 or RSASSA-PSS), ECDSA and EdDSA (Ed25519).

### Encryption vs hashing vs signing

| | Encryption | Hashing | Digital signature |
|---|---|---|---|
| Uses a key | Yes | No (HMAC does) | Yes (private key to sign) |
| Reversible | Yes, with the key | No | Verifiable, not reversible |
| Provides | Confidentiality | Integrity | Authenticity, integrity, non-repudiation |
| Output size | Similar to input | Fixed | Depends on key size |

### How a certificate uses all of this

A certificate is itself a signed document. The CA takes the certificate contents (subject, public key, validity, extensions), hashes them, and signs the hash with the CA's private key. When a client receives the certificate, it:

1. Hashes the certificate contents.
2. Verifies the signature using the CA's public key, which it already trusts from the Trusted Root store.
3. If this matches, the client knows the certificate is genuine and has not been altered.

This is the chain of trust in a nutshell, and it is the topic that the next modules build on. Every time you see a SHA-256 with RSA signature algorithm in a certificate, it is this process.

## Quick Revision

- PKI = trust framework that binds public keys to identities through certificates.
- Cryptography goals: confidentiality, integrity, authentication, non-repudiation.
- Symmetric = one key, fast, used for data. Asymmetric = key pair, slow, used for key exchange and signatures.
- Hybrid encryption = asymmetric to exchange the key, symmetric to protect the data.
- Hash = fixed-size one-way fingerprint. Use SHA-256 or better. MD5 and SHA-1 are broken for security.
- Digital signature = hash signed with the private key, verified with the public key.
- Encrypt with the receiver's public key. Sign with your own private key.
- A certificate is a public key plus identity, signed by a CA.

## Common Interview Questions

**What is the difference between symmetric and asymmetric encryption?**
Symmetric uses one shared key and is fast. Asymmetric uses a public and private key pair and is slower, but solves key distribution and enables signatures.

**Why do we use both in TLS?**
Asymmetric is used for authentication and key exchange, then symmetric is used for the actual data because it is much faster.

**Is hashing the same as encryption?**
No. Hashing is one-way and keyless, encryption is reversible with a key.

**What does a digital signature give you that a hash alone does not?**
A hash can be recalculated by anyone, including an attacker who changes the data. A signature ties the hash to a private key, so it proves who created it.

**Why was SHA-1 retired?**
Practical collision attacks were demonstrated, so it could no longer guarantee that two different documents would not share a hash.

**Which key do you use to sign, and which to verify?**
Sign with the private key, verify with the public key.

**What is forward secrecy?**
Session keys are generated per session using ephemeral key exchange, so a later private key compromise does not expose past traffic.
