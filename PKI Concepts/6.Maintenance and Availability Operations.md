# Maintenance and Availability Operations

A PKI is not finished once it is deployed. Certificates expire, CRLs have a limited life, databases grow, and the people who built the system move on. Most real PKI outages are not caused by attacks but by missed routine tasks: an expired CRL, a full disk, a CA certificate that was not renewed in time, or a backup that cannot be restored. This module covers how to keep a Microsoft PKI healthy and available day to day.

The module is split into these topics:

- **CA Maintenance** - backup, restore, CA certificate renewal and database upkeep
- **CRL Maintenance** - keeping revocation data fresh and published
- **Exit Modules** - what the CA does after issuing, and the related policy modules
- **CA Monitoring** - what to watch, which tools to use and what to alert on
- **Documentation and Processes** - runbooks, schedules and ownership
- **Module Review**

---

## CA Maintenance

### Maintenance mindset

The aim is simple: the CA must always be **available** (clients can enroll and validate), **recoverable** (it can be rebuilt from backup) and **understood** (somebody other than the original builder can operate it). Maintenance is the set of regular tasks that keep these three true.

### Backup

There are two different kinds of backup, and mixing them up is a common mistake.

| Type | What it contains | What it is good for |
|---|---|---|
| Database backup | The CA database and its log files | Rolling back database changes, for example before a cleanup |
| Full CA backup | The database and logs, the CA certificate and private key, and the CA configuration (registry settings) | Rebuilding the CA after a failure |

A database-only backup is not enough to restore a CA after a total loss, because without the CA private key the restored database is useless.

Common methods:

- **Certification Authority console:** right-click the CA, choose *All Tasks > Back up CA*, and select the private key and CA certificate, and the certificate database and log. Set a strong password for the key file.
- **certutil:** `certutil -backup C:\CABackup` backs up the key, certificate, database and logs. `certutil -backupDB C:\CABackup` backs up the database only, and `certutil -backupKey C:\CABackup` backs up only the key and certificate.
- **PowerShell:** the `Backup-CARoleService` and `Restore-CARoleService` cmdlets (Windows Server 2012 R2 and later).
- **System State backup** with Windows Server Backup, which also includes the CA private key on Windows Server 2012 and later.
- Also export the registry configuration of the CA (the CertSvc configuration key) and keep a copy of `CAPolicy.inf` and the CDP/AIA settings.

If the CA key is in an HSM, the key is not in the backup file. You must back up the HSM key material or key-sharing cards according to the vendor's process.

Backup practice:

- Back up the issuing CA regularly (for example daily or weekly, and always before any change).
- Back up the offline root after every power-on session where something changed, and store several copies in different secure places.
- Keep backups offline or immutable, and protect the key backup with a strong password held by the right custodians.
- Test a restore at least once a year, on a separate server. A backup that has never been restored is only a hope.

### Restore

After a failure the usual order is:

1. Build a server with the same computer name and domain membership (for an Enterprise CA).
2. Install the AD CS role, choosing to use an existing private key (or restore the key from the backup).
3. Restore the database, logs and configuration with the console wizard, `certutil -restore C:\CABackup`, or `Restore-CARoleService`.
4. Restore the registry configuration if it was backed up separately, then start the CA service.
5. Publish a new CRL, and verify with `PKIView.msc` and a test enrollment.

If the CA key was a software key and the CA is restored on a different computer, the key and certificate must be imported into the correct store so the CA can find them.

### Renewing the CA certificate

A CA certificate has a fixed lifetime. If it expires, every certificate that the CA issued stops validating, so renewal must be planned well ahead (a common rule is to start renewing when about half to two-thirds of the lifetime has gone, and certainly well before the last year).

Two ways to renew:

| Renewal type | Effect |
|---|---|
| Renew with the same key | A new certificate with the same key pair and a new validity period. Simple, and existing certificates keep validating without change. Command: `certutil -renewCert ReuseKeys`. |
| Renew with a new key | A new key pair and a new certificate. This is the better choice from a security point of view, and is required when the key length or algorithm must change. It creates a new key-set and a certificate with an index, such as `CAName(1)`. The CRL file name also gets a suffix, for example `CAName(1).crl`. |

Notes:

- For a subordinate CA, the renewal request has to be signed by the parent CA, in the same way as the original installation (Module 03). The parent must also have enough validity left, because a CA certificate cannot outlive its parent.
- The `CAPolicy.inf` renewal settings (key length, validity) are used during renewal, so keep the file in place.
- After renewal with a new key, the CA has more than one valid certificate and key. Old certificates keep validating against the old key, so you will have several CRLs during the transition, and the `%8` variable in the CDP URL (Module 02) must be in place so each CRL has a unique name.
- Publish the new CA certificate to the AIA location and, for domain clients, to Active Directory (`certutil -dspublish -f NewCA.crt SubCA`).
- Check the chain and revocation afterwards with `certutil -verify -urlfetch`.

### Database maintenance

The CA database (an ESE database in the `CertLog` folder) grows with every request and certificate. Without care it becomes large, slow to back up and slow to restore.

- **Remove failed and denied requests.** They are of no value after a short time. `certutil -deleterow <date> Request` removes requests (for failed, denied and pending ones, check the available options with `certutil -deleterow -?`).
- **Remove old expired certificates and their requests**, once your retention policy allows. `certutil -deleterow <date> Cert` deletes the certificate rows. Keep records for as long as your audit and legal rules require.
- **Always take a database backup first.** Deleting rows is not reversible.
- **Compact the database** (offline defragmentation) after large deletions, because deleting rows does not shrink the file. Stop the CA service, take a backup, then use the ESE tool: `esentutl /d <path to CAName.edb>` and start the service again. This needs free disk space roughly equal to the database size.
- **Watch the disk** that holds the database and logs. A full disk stops the CA.
- Do these tasks in a maintenance window, and confirm after restart that the CA is working and issuing.

### Other routine CA tasks

- Patch the servers (issuing CA, web server, Online Responder) on a schedule. The offline root must be powered on from time to time for this, together with its CRL renewal.
- Review published templates and their permissions every quarter. Remove templates that are not used.
- Review permissions on the CA itself, on the template objects and on the Public Key Services container in Active Directory.
- Check the certificates the PKI itself depends on, such as the OCSP Response Signing certificate, enrollment agent certificates, the NDES certificates, and the TLS certificate of the web server.
- Check time synchronisation. CRL and certificate validation depend on correct time.
- Plan for capacity and end of life of the server operating system, the HSM and the hash/key algorithms.

## CRL Maintenance

CRLs are the single most common source of PKI outages, because they expire on their own if nobody refreshes them. Module 02 explained how CRLs work. This section covers keeping them healthy.

### Know your CRL schedule

Write down, for every CA, the CRL period, delta CRL period, overlap, the publishing locations and who is responsible. A typical example:

| CA | Base CRL | Delta CRL | Who publishes |
|---|---|---|---|
| Offline Root CA | 26 to 52 weeks | None | Manual (power on, publish, copy) |
| Issuing CA | 1 week | 1 day | Automatic by the CA service |

### Offline root CRL procedure

The root CRL must be renewed before it expires, with enough margin for mistakes. A common practice is to renew it when roughly a third of its life is left, and put a calendar reminder and a ticket in place long in advance.

1. Power on the root (isolated), check the time and apply any planned patches.
2. Publish a new CRL: `certutil -crl`.
3. Check the new file in the `CertEnroll` folder with `certutil -dump RootCA.crl` and confirm the This Update and Next Update dates and the new CRL Number.
4. Copy the `.crl` file (and the CA certificate if it changed) to removable media.
5. Copy it to the web server (the CDP location) on every web server that serves it.
6. Publish to Active Directory from a domain-joined machine if LDAP locations are used: `certutil -f -dspublish RootCA.crl`.
7. Verify from a client with `certutil -urlfetch -verify` against a certificate issued by the issuing CA, and check `PKIView.msc`.
8. Back up the root if anything changed, power it off and store it securely.
9. Record the new expiry date and schedule the next renewal.

### Issuing CA CRL tasks

- The CA publishes the base and delta CRLs automatically at the configured intervals. Check that the CA can write to every publishing location (local folder, web server share, Active Directory). If it cannot, the CRL is created locally but clients never see it.
- If the web server is a separate machine, make sure the files really arrive there (by a share, DFS, a scheduled copy, or a CA publishing script) and that the copy runs often enough compared with the delta CRL period.
- After changing the CRL period or the publishing locations, the change applies only at the next publication, so run `certutil -crl` and restart the CA service where needed.
- After an urgent revocation, publish immediately with `certutil -crl` so clients can see it sooner (and remember the client-side cache from Module 02).
- If the CA certificate was renewed with a new key, check that the new CRL name suffix is published and the CDP URLs match it.
- Watch the CRL size. A very large base CRL is slow to download, which suggests shortening certificate validity, removing unnecessary issuance, or using delta CRLs and OCSP.

### Web server and high availability

- Keep the CDP/AIA web site on more than one server behind a load balancer or DNS, for any business-critical PKI, and make sure all copies hold the same files.
- Keep the IIS settings from Module 02 (anonymous access, double escaping for delta CRLs, no HTTPS redirect for CDP paths).
- Monitor the HTTP location itself from the point of view of clients.

### Verifying CRL health

A simple way to check how many days are left on a CRL, using certutil output, is:

```
certutil -dump IssuingCA.crl | findstr /i "ThisUpdate NextUpdate NextCRLPublish"
```

For a check against the real URL, download the file from the CDP and run the same command on the downloaded copy, then compare the Next Update date with today. Automate this and alert when the remaining time is shorter than the agreed margin (see the monitoring section).

## Exit Modules

### Policy modules and exit modules

The Certificate Services engine (`certsrv.exe`) works together with two kinds of plug-in:

- **Policy module** - decides what to do with a request. It checks the request against the rules for issuance, and the default action is to approve, deny or mark as pending. The default policy module has two policies, one for Enterprise CAs (templates and Active Directory) and one for Standalone CAs. A CA can load only one policy module at a time.
- **Exit module** - acts after the CA has issued a certificate or published a CRL, by delivering or publishing the result. A CA can run several exit modules at the same time.

The default modules are in the files `certpdef.dll` (policy) and `certxds.dll` (exit). They can be replaced or supplemented by custom or vendor modules.

### What the default exit module does

- **Publishes certificates and CRLs to Active Directory.** This is on by default for an Enterprise CA (for example user certificates in the user object, CA certificates in the AIA container, and CRLs in the CDP container). The option is not available on a standalone CA.
- **Publishes certificates and CRLs to the file system.** This is on by default for a Standalone CA, and off by default for an Enterprise CA. Even when enabled, publication only happens if the request specifies a file location.
- **Sends an e-mail notification** when a certification event occurs, such as a certificate being issued or a request becoming pending. This is configured through the registry and is a legacy feature that most teams replace with event-based monitoring.

The default exit module also handles the publication interval, which is why CRL publishing problems often show up as exit module errors.

### Configuring the modules

In the Certification Authority console, right-click the CA, choose *Properties*, and use the *Policy Module* and *Exit Module* tabs, then *Properties* for the module. The default policy module lets you set whether a request on a Standalone CA is held as pending or issued automatically. For security, an offline root should keep the setting that holds all requests as pending, so an administrator approves each one.

### Custom and third-party modules

- Custom exit modules can publish to other places, such as a web page or a third-party directory.
- Policy modules for NDES are provided by device management products so that SCEP enrollment can be authenticated better. Microsoft notes that no policy module is included in the box, and that management products such as Configuration Manager supply one. This is how over-the-air enrollment of mobile devices can be done more safely.
- Because custom modules run inside the CA process and can influence what gets issued, they are a security-sensitive part of the CA. Install only supported, trusted modules, test them, and track them in your inventory.

### Operational points

- If an exit module fails, the CA logs an error (for example an Event ID 46 in the Application log, saying that an exit module method returned an error). The certificate may still have been issued, but the publishing step failed, so check where the certificate or CRL was supposed to go.
- Changes to the policy or exit modules, and to CDP and AIA settings, should appear in the CA's audit log, so alert on them (see Monitoring).
- If a CA has publishing problems to Active Directory, check the CA computer's permissions on the Public Key Services containers and the AD replication state.

## CA Monitoring

### What to monitor

| Area | What to check | Why |
|---|---|---|
| Service health | CA service (CertSvc) running, CA responds to `certutil -ping` | Clients cannot enroll if the CA is down |
| CRL validity | Days left on every base and delta CRL, including the root CRL | An expired CRL breaks validation for everyone |
| CRL and AIA reachability | HTTP (and LDAP) locations return the right files | Clients must be able to download them |
| CA and PKI certificates | Expiry of CA certificates, OCSP signing, enrollment agents, NDES, web server certificates | Silent expiry causes outages |
| Online Responder | Revocation configuration status, signing certificate, array health | OCSP failures cause revocation errors |
| Database and disk | Database size, free space on the database and log volume | A full disk stops the CA |
| Issuance activity | Requests, issued, failed, denied and pending counts | Spikes can show abuse or a broken template |
| Security events | Certificate issued, denied or revoked; configuration, permission and template changes; CA start and stop; backup and restore | Detect tampering and misuse |
| Backups | Latest successful backup time | Proof you can recover |
| Platform | Time sync, patching, antivirus/EDR state, resource use | Basics for a Tier 0 server |

### Tools

- **PKIView.msc (Enterprise PKI).** A quick visual health check showing each CA and the status of its CDP and AIA locations, including expired CRLs.
- **certutil.** `certutil -ping` (CA reachable), `certutil -CAInfo` (CA details), `certutil -pingadmin` (admin interface), `certutil -URL` and `certutil -urlfetch -verify` (URL and chain checks), `certutil -dump` (inspect files).
- **Certification Authority console.** Issued, Revoked, Pending and Failed Requests nodes, and the CA properties.
- **Event logs.** The Application log (CertSvc events), the Security log with CA auditing enabled (Module 03), and the CAPI2 operational log on clients.
- **Performance counters.** The Certification Authority counters show request rates and failures and can be graphed.
- **System Center Operations Manager.** Microsoft publishes a management pack for AD CS that monitors CA health.
- **SIEM.** Forward CA Security and Application logs to your SIEM (such as Splunk or Microsoft Sentinel) and build alerts there. This is the best place for security-related alerts and for correlation with other events.
- **Scripts and scheduled tasks.** Small PowerShell scripts that check CRL dates, URL availability and certificate expiry, and send mail or create tickets.

### Important events

Microsoft's *Securing PKI* guidance has a full table of CA events with suggested priorities, and it is worth reading to build your alert list. Examples that are commonly used include:

- Certificate request received, issued (4886 and 4887) and denied (4888)
- Certificate revoked (4870)
- CA service started and stopped
- CA backup and restore started and completed
- Changes to CA configuration, permissions, templates, or CDP/AIA and policy/exit module settings
- Rows deleted from the certificate database
- The CA failing to start because of database problems
- Exit module errors (Event ID 46)

Confirm the exact event IDs for your Windows Server version in the Microsoft appendix before you build alerts.

### Suggested alert thresholds

These are starting points only. Tune them to your own CRL periods and response times.

| Item | Warning | Critical |
|---|---|---|
| Offline root CRL | 60 days left | 30 days left |
| Issuing CA base CRL | 3 days left | 1 day left |
| Issuing CA delta CRL | 12 hours left | 4 hours left |
| CA certificate | 12 months left | 6 months left |
| OCSP signing, enrollment agent, web server certificates | 30 days left | 7 days left |
| Free disk on CA database volume | below 20 percent | below 10 percent |
| CA service | Not applicable | Stopped |
| CDP/AIA URL | Slow responses | Not reachable or wrong file |

### Monitoring from the client point of view

Server checks can all look healthy while clients still fail, for example because of a firewall, a proxy or a CDN. Add at least one **synthetic test** that runs from a normal client network, downloads the CRLs and CA certificates, and validates a test certificate chain. This is the check that best matches what users experience.

## Documentation and Processes

A PKI that exists only in one person's head is a risk. Documentation and agreed processes make the PKI survive staff changes, audits and emergencies.

### What to document

- **Architecture:** a diagram of the hierarchy, servers, web servers, Online Responders, NDES/CEP/CES, load balancers and network paths.
- **CA details:** CA names, server names, key lengths, algorithms, validity dates, certificate thumbprints, key storage (software or HSM) and where the keys and backups are kept.
- **Configuration:** `CAPolicy.inf` files, CDP and AIA URLs, CRL periods and overlap, exported registry settings, IIS settings and DNS aliases.
- **Certificate templates:** purpose, owner, validity, key settings, who can enroll, and which CAs publish each one.
- **Roles and responsibilities:** who is CA administrator, certificate manager, auditor and backup operator, and who holds HSM cards, passwords and the safe.
- **Policies:** the certificate policy and Certification Practice Statement (CPS) if you have them, and your key and algorithm standards.
- **Dependencies:** which applications, devices and services use which certificates.
- **Contacts:** vendor support, internal teams and the escalation path.

### Runbooks (standard operating procedures)

Write each recurring or critical task as a step-by-step procedure that someone else could follow:

- Renew the offline root CRL
- Renew a CA certificate (same key and new key)
- Back up and restore a CA
- Add or change a certificate template, and publish it
- Revoke a certificate and publish a CRL urgently
- Add or replace a web server for the CDP/AIA
- Rebuild or migrate a CA
- Respond to a CA compromise or a stolen key
- Respond to an expired CRL or an expired CA certificate
- Power-on and handling procedure for the offline root (including who must be present)

A good runbook has the purpose, who may do it, prerequisites, exact commands, how to verify, how to roll back, and who to inform.

### Recurring task calendar

| Frequency | Task |
|---|---|
| Daily | Check alerts, CA service, CRL validity, backup success, failed and pending requests |
| Weekly | Review issuance and denied-request trends, disk and database size |
| Monthly | Patch and reboot plan, review the PKIView status, review security event reports |
| Quarterly | Template and permission review, database cleanup, check expiry of all PKI-related certificates |
| Every 6 to 12 months | Offline root power-on: CRL renewal, patching, backup (before CRL expiry) |
| Yearly | Full restore test, disaster recovery exercise, review of documentation, policies and algorithms |
| Before expiry | CA certificate renewal, HSM and hardware lifecycle, operating system end of support |

### Change management and records

- Treat the PKI as Tier 0. Every change to CA configuration, templates, CDP/AIA or modules goes through change control with a reviewer.
- Keep a change log and store the documents in a controlled, backed-up location (not only on the CA).
- Keep audit evidence: logs, backup records, restore tests and the ceremony records for root key operations.
- Review the documentation at least once a year and after any major change, and have a second person follow a runbook now and then to prove that it works.
- Run a tabletop exercise for the worst cases (lost root, compromised issuing CA, expired CRL) so that the response is rehearsed.

## Module Review

- Keep the PKI **available, recoverable and understood**. Most outages come from missed routine tasks.
- A database backup is not a full CA backup. The full backup includes the CA key, certificate and configuration. Use `certutil -backup`, the console, or `Backup-CARoleService`, store backups offline, and test restores.
- Renew the CA certificate well before it expires, with the same key (`certutil -renewCert ReuseKeys`) or a new key. With a new key the CRL gets a suffix and the `%8` variable must be in the CDP URL. A subordinate CA's renewal is signed by its parent.
- Keep the CA database under control by deleting old failed requests and expired certificates (with a backup first), compacting offline, and watching disk space.
- CRLs expire on their own. Know every CRL's schedule. Renew the offline root CRL early, copy it to the web servers and Active Directory, and verify from a client. After an urgent revocation publish a new CRL immediately.
- The policy module decides to approve, deny or hold a request (only one active). Exit modules act after issuance or publishing (several can be active). The default exit module publishes to Active Directory (Enterprise CA) or the file system (Standalone CA). Custom modules are security-sensitive.
- Monitor the service, CRL and certificate expiry, URL reachability, disk, issuance, security events and backups. Use `PKIView.msc`, certutil, event logs, performance counters, SCOM and your SIEM, and add a client-side synthetic test.
- Document and rehearse. Keep architecture, configuration, templates and roles written down, with runbooks, a recurring task calendar, change control, and regular restore and disaster recovery exercises.

## Common Interview Questions

**What is the difference between a CA database backup and a full CA backup?**
A database backup holds only the database and logs. A full backup also has the CA private key, certificate and configuration, and is needed to rebuild the CA.

**How often should the offline root CRL be renewed, and what happens if it expires?**
It depends on its CRL period (often 6 to 12 months). Renew it well before expiry. If it expires, revocation checking fails for every certificate in the hierarchy.

**How do you renew a CA certificate?**
Renew with the same key (`certutil -renewCert ReuseKeys`) or with a new key. For a subordinate CA, the request is signed by the parent CA. Then publish the new certificate to the AIA and Active Directory and verify the chain.

**What changes after renewing a CA certificate with a new key?**
The CA gets a new key and certificate index, and the CRL file name gets a suffix, so the CDP URL needs the `%8` variable, and several CRLs exist during the transition.

**How do you keep the CA database small?**
Delete old failed and expired entries with `certutil -deleterow` (after a backup), compact it offline with `esentutl`, and monitor disk usage.

**What is the difference between a policy module and an exit module?**
The policy module decides whether a request is approved, denied or pending, and only one is active. An exit module acts after issuance or CRL publishing, such as publishing to Active Directory or the file system, and several can run.

**What would you monitor on a CA?**
Service health, CRL and certificate expiry, CDP/AIA availability, database and disk, issuance and failures, security events, backups, and a client-side test of the chain.

**Which tools help you check PKI health quickly?**
`PKIView.msc`, `certutil -ping`, `-CAInfo`, `-urlfetch -verify` and `-dump`, the CA console and the event logs.

**What should a PKI runbook contain?**
Purpose, who can run it, prerequisites, exact steps and commands, verification, rollback and who to notify.

**What would you do if the issuing CA certificate was about to expire?**
Start the renewal immediately, get the request signed by the root (a root power-on session), install and publish the new certificate and CRL, check the chain from clients, and update the runbook and the expiry calendar.
